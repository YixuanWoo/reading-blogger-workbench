## 2. 接入方式：四条路，只有一条不用建应用（v2 重写）

### 2.1 你给的那个 H5 文档：不适用，理由说清

`open.feishu.cn/document/client-docs/h5/` 是 **H5 JSAPI**。它的定位是
"让你写一个网页，跑在**飞书客户端里面**，调飞书的原生能力" ——
能力清单是：聊天、联系人、剪贴板、扫码、窗口、导航栏、震动、截屏监听…
**里面没有任何一条是"读我的多维表格"**。

更关键的是：除 `requestAuthCode` / `closeWindow` / `requestAccess` 三个之外，
**其余 JSAPI 全部要求"网页应用鉴权"** —— 而"网页应用"本身就是一个要建的应用。
所以这条路**既解决不了问题，也没省掉建应用**。此路不通。

### 2.2 ★ 官方通道：多维表格个人授权码 `PersonalBaseToken`

飞书有一个**专门为"不想建应用"设计的鉴权体系**，官方原话：

> 「我们推出了多维表格独立的鉴权体系，开发者可以在网页端获取某个多维表格的授权码
> **PersonalBaseToken**，即可在服务端读取和写入数据……**
> **优点：无需申请飞书自建应用或上架到飞书应用目录。**」

它的三个特点，正好对上你的场景：

| 特点 | 对我们的意义 |
|---|---|
| **在网页端点两下就能拿** | 不用进 `open.feishu.cn`，不用建应用，不用等审核 |
| **接口定义与开放平台 OpenAPI 完全一致** | §4 的映射逻辑、字段格式处理**一行都不用改**，纯粹换个域名和请求头 |
| **只对那一张表有效，默认永久有效** | 权限面比"一个应用能摸到全公司"小得多；可随时在表里关闭或重置 |

**用法就两行**（这就是全部）：

```
域名：https://base-api.feishu.cn          （Lark 用 https://base-api.larksuite.com）
路径：/open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records   ← 与 OpenAPI 一模一样
鉴权：Header  Authorization: Bearer {PersonalBaseToken}
```

**顺带解决了 §4.3 那个 wiki 大坑**：官方推荐用表里的 **【开发工具】插件**直接读出当前 Base 的
`AppToken`（又称 BaseId）—— 它在 `/wiki/xxx` 路径下**照样能给**，于是不用再调
`wiki/v2/spaces/get_node` 换 token，`wiki:wiki:readonly` 权限也不需要了。

**代价（必须写进设计）**：

- ⚠ **单文档限频 2 QPS**（多文档可并发）。几百本书的量级完全够，但**批量写必须限速**（§4.1）
- 身份 = **授权码的生成者**（即你本人），不是"某个应用"—— 所以写进去的记录，最后编辑人是你自己
- ⚠ 授权码是**明文凭据**：通过它可读可编辑这张表，**不能外传**（本方案的存法见 §3）

### 2.3 其余三条路（记录备选，主力不用）

| 路线 | 要不要建应用 | 能读 | 能写 | 定位 |
|---|---|---|---|---|
| **A. 个人授权码 PersonalBaseToken** | ❌ 不用 | ✅ | ✅ | ★ **本项目主力** |
| B. 企业自建应用 + 把表共享给应用 | ✅ 要（且个人号得先"升级为团队"） | ✅ | ✅ | 备选：将来要管多张表 / 多人协作时 |
| C. 自动化流程 Webhook（"接收到 webhook 时"→"新增记录"） | ❌ 不用 | ❌ | ✅ | 只做**推送方向**的兜底（见下） |
| D. 多维表格插件（`@lark-base-open/js-sdk`） | ❌ 不用 | ✅ | ✅ | 手动导出/拉取的兜底 |
| E. H5 JSAPI（你给的那个文档） | ✅ 要 | ❌ | ❌ | **不适用** |
| F. `lark-cli` | ✅ 要（它替你建） | ✅ | ✅ | **只作探路工具**，不作产品依赖 |

**关于路线 C（值得记一笔）**：多维表格的「自动化」里有个触发条件叫「**接收到 webhook 时**」，
动作可以配成「**新增记录**」写回本表。于是本地只要 `POST` 一个 URL（带一个自动化自己生成的
Bearer token，**与开放平台应用无关**）就能往表里塞数据 —— 零应用、零授权码。
但它**不能读**，且逻辑写在飞书侧的自动化里（改起来要到网页端改）。所以只作兜底。

**关于 `lark-cli` 是不是"专门给 agent 用的"**：定位上确实是（官方文案"给 Agent 一双操作飞书的手"），
但技术上就是个普通 CLI，不是只能给 agent 用。它的价值在于把"建应用 + 授权 + 调接口"包成一条命令
——官方 FAQ 自己写着「**CLI 只是提供一键创建应用的能力**，应用的管控仍然 follow 企业统一管控规则」，
且「配置应用时**默认会创建一个新应用**」。
**结论：它不改变"得有应用"这件事，所以它能省掉的是手工点击，不是权限关。**
在本项目里它只用来**探路**（§2.4），产品里一律走 HTTP。

### 2.4 第 0 步：15 分钟探路（动手写代码之前必须先做）

**为什么必须先做**：万一你的表（或你的账号）不认这条路，整个接入设计要换，越早发现越便宜。

**做法（在终端里做，不用写代码）**：

```bash
# ① 在表里拿两样东西（浏览器操作，约 3 分钟）
#    打开那张多维表格 → 插件 / 开发工具 → 读出 AppToken；同一面板里生成并复制授权码
#    （旧文档写的入口叫「自定义插件 → 获取授权码」，现在界面可能已改名，以实际为准）

# ② 用 curl 打一枪（约 1 分钟）—— 这一步通了，接入就通了
curl -X GET \
  "https://base-api.feishu.cn/open-apis/bitable/v1/apps/<app_token>/tables/<table_id>/records?page_size=5" \
  -H "Authorization: Bearer <personal_base_token>"
```

**判定**：
- ✅ 返回 `{"code":0,"data":{"items":[...]}}` → 收工，按本方案开工。
- ⚠ 返回 `code` 非 0 → 把错误码发我（`1254302` = 没有该表权限；`99991663` = 授权码无效/已关闭）。
- ❌ 界面里找不到"获取授权码"入口 → 走**备选 B**（先建应用；个人号需先在客户端
  「设置 → 升级为团队」建一个只有你自己的免费团队，然后就能进开发者后台）。
  **备选 B 的完整步骤保留在本文件 v1 版本里**（表共享给应用那一步是 `1254302` 的常见来源）。

> ★ 探路用 `curl` 而不是 `lark-cli`（v1 写的是用 CLI）：既然主力路线不需要应用，
> 就用最朴素的 `curl` 验，**验的东西和将来 C# 里要写的东西完全同构**，没有中间层干扰。

## 3. 数据放哪（本地）

**结论**：`%APPDATA%\翊瑄的工作台\reading\` —— 和「灵感池」同一个家。
理由：跟具体项目无关的数据放这儿，是这个工程已经定过的规矩（`AppConfig.DataDir`）。

```
%APPDATA%\翊瑄的工作台\
  config.json                     ← 已有
  inspiration.json                ← 已有（灵感池）
  reading\
    books.json                    ← ★ 主数据（本地永远是完整可用的）
    schema.json                   ← 字段映射（本地字段 ⇄ 飞书字段名 + 类型）
    sync-log-<时间戳>.json        ← 每次同步的账本（可回滚，同 reindex-log 风格）
    backup\
      books-<时间戳>.json         ← 每轮同步前自动快照（保留最近 20 份）
```

**凭据单独放**（含密钥的东西不跟数据混）：
`%LOCALAPPDATA%\LiteCut\feishu-creds.json`，**用 Windows DPAPI 加密**（`ProtectedData`，.NET 内置零依赖）。
里面就存三样：`AppToken` / `TableId` / `PersonalBaseToken`（授权码那一项必须加密）。

放 `%LOCALAPPDATA%` 而不是 `%APPDATA%` 的理由和桥接凭据一样：**不随数据目录被一起备份/上传**。

## 4. 飞书侧的契约

### 4.1 用到的接口（就 4 个，且都在同一域名下）

| 用途 | 方法与路径（前缀 `https://base-api.feishu.cn`） |
|---|---|
| 列字段名（设置页给你选） | `GET /open-apis/bitable/v1/apps/:app_token/tables/:table_id/fields` |
| 查全部记录 | `POST /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records/search`（page_size ≤ 500，翻页到 `has_more=false`） |
| 批量新增 | `POST /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records/batch_create`（单次 ≤ 500） |
| 批量更新 | `POST /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records/batch_update`（单次 ≤ 500） |

**与"标准 OpenAPI 路线"的差异只有两处**（官方原话就是只有这两处）：
① 域名换成 `base-api.feishu.cn`；② 鉴权 Header 用 `Bearer {PersonalBaseToken}`。
**没有换 token 的接口**（不需要 `tenant_access_token`，也不需要 2 小时续期逻辑）——
这是 v2 比 v1 少写代码的地方。

> ⚠ 老接口 `GET .../records`（列出记录）官方已标注**「历史接口，已不推荐使用」**，
> 新代码一律用 `records/search`。

**必须处理的两条约束**：
- ★ **限频 2 QPS（单文档）** → 客户端里加一个**串行节流器**（相邻请求间隔 ≥ 500ms），
  批量接口优先（一次 500 条），并把 `code=1254291 Write conflict`（**同一张表不支持并发写**）
  与限频退避一起处理。几百本书：读 1~2 次请求、写 1~2 次请求，**体感上毫无延迟**。
- `automatic_fields: true` —— 否则**拿不到 `last_modified_time`**，而它是判"远端改没改"的关键依据之一
- `page_size: 500` —— 默认才 20，不设就要翻几十次

### 4.2 ★ 字段格式陷阱（这个坑最深，我提前给你标出来）

飞书多维表格的字段值**不是朴素 JSON**，同一个"看起来是文本"的字段，类型不同格式完全不同：

| 飞书字段类型 | API 里长什么样 | 陷阱 |
|---|---|---|
| 单行文本 | `"标题"` | 有时会返回成 `[{type:"text",text:"标题"}]` 数组 —— **同一张表不同字段都可能不一样** |
| 多行文本 | `"内容"` 或 `[{text,type}]` | 由 `text_field_as_array` 决定，**写回时必须和读到的格式一致** |
| 单选 | `"已读"` | 写回时值**必须是已存在的选项**，否则报 `1254062`（会悄悄新建选项） |
| 多选 | `["小说","历史"]` | 是数组，空值可能是 `null` 而不是 `[]` |
| **日期** | `1674206443000` | ★ **13 位毫秒时间戳，且是 UTC**。直接显示会**差 8 小时**，"读完日期"经常因此差一天。必须按本地时区换算 |
| 数字 | `"100"`（**字符串**） | ★ 数字字段返回的是**字符串**，且"评分"可能是数字 1~5 也可能是单选星级 |
| 复选框 | `true` |
| 附件 | `[{file_token,name,size,type,url}]` | 封面图要走 `file_token` 下载，多一步 |
| 人员 | `[{id,name,en_name,...}]` | 要额外权限才拿得到姓名，否则只有 id |

**对策**：这些差异**全部收敛在一个文件里**（`ReadingFieldMap.cs`），
页面和同步引擎**永远只面对本地模型**（干净的 C# 类型）。
将来你改了表结构、换了字段类型，只改映射，不动别处。

### 4.3 ★ 工作台怎么知道"是哪张表"：它不认账号，只认三个字符串

这是本方案最容易被误解的一点，单独讲清。

**工作台不会去"你的账号里找表"。** 这条路线里没有"账号"这个概念 ——
不需要登录、不需要扫码、不需要 OAuth 弹窗、不需要管理员。它手上永远只有三个字符串：

| # | 名字 | 指向哪一层 | 从哪抄 |
|---|---|---|---|
| ① | `AppToken`（又称 BaseId） | **哪个多维表格文档** | 表里的插件 /【开发工具】面板；或 URL 里 `base/` 后面那串 |
| ② | `TableId` | **该文档里的哪张数据表** | 同一个面板；或 URL 里 `?table=` 后面那串 |
| ③ | `PersonalBaseToken`（授权码） | **开这扇门的钥匙**（不是层级，是钥匙） | 同一面板点「获取授权码」生成 |

- ★ **为什么是三样不是两样**：一个多维表格**文档**（①）里可以有好几张**数据表**（②），
  光有文档 ID 不足以定位到你要同步的那张表。这就是设置页要填三个的原因。
- ★ **授权码的边界是「整个文档 ①」**（含该文档下所有数据表），**不是全账号的钥匙**。
  这正是它比"建一个应用"安全的地方：应用能摸到你所有有权限的表，授权码只开一扇门。
  丢了就在表里重置一次，别的表不受影响。
- ★ **URL 两种形态**：`feishu.cn/base/<app_token>?table=<table_id>` 直接从 URL 抄；
  `feishu.cn/wiki/<wiki_token>?...` **URL 里没有 app_token**，但用表里的【开发工具】插件照样能读出
  （v1 里那个额外的 `wiki/v2/spaces/get_node` 调用 + `wiki:wiki:readonly` 权限**已删**）。

**代入你的场景**：① 是你那张「读书统计」多维表格，② 是它里面的「书单」数据表，
③ 从同一张表里生成 —— 三个都在同一个面板里，一分钟抄完，粘进工作台设置页即可。
**记录级**的对应则是另一回事：同步到本地后靠 `record_id` 认人（存在每本书的本地记录里）。

## 5. 同步引擎（这才是真正的难点）

### 5.1 三条铁律

**铁律一：先定义"边界"，再谈"同步"。**
不是所有字段都参与同步。分两层：
- **共管字段**（书名/作者/状态/评分/日期/分类…）→ 两边都能改，进同步
- **本地专属字段**（比如"我自己的私密笔记"）→ **永不推送**，飞书那边改了也不动它

只有共管字段参与"指纹"计算 —— **这是减少冲突面的根本手段**。
（反面：把所有字段都丢进同步，冲突率会高到没法用。）

**铁律二：同步是显式动作，不做后台自动轮询。**
三个按钮：`从飞书拉取` / `推送到飞书` / `双向同步`
★ 这条和你已经定过的规矩一脉相承 ——「**所有环节的交接只走「应用到下游」**」。
同一个心智模型：**没点按钮 = 另一边读的还是上一版**。你会立刻上手，因为工作台就是这么运转的。
离线/没授权时按钮灰掉，但**看自己的书单照旧**（本地永远是完整可用的）。

**铁律三：删除不双向。**（见 §5.4，这是防丢数据最重要的一条）

### 5.2 算法：三方比对（不是"复制"）

普通"同步"的想法是"把新数据拷过去"，那必然丢数据。正确做法是**记住上一次对齐时的状态**：

```
每条记录存一个 SyncedFingerprint = 上次同步成功时，"共管字段"的指纹
（复用工程里已有的 FNV-1a 64 位思路 —— render-manifest.json 判"待重渲"用的就是它）
```

每轮同步：
```
1. 读本地全部记录 → 按 FeishuRecordId 建索引
2. 调 search 翻页拉飞书全部记录 → 按 record_id 建索引
3. 逐条判：
   ┌ 本地 id 为空                    → 【本地新建】→ 待推送
   ├ 飞书里找不到这个 id             → 【飞书已删】→ 标 RemoteMissing，★不自动删，等你裁决
   └ 两边都有：
       本地指纹 ≠ SyncedFingerprint  → "本地改过"
       远端指纹 ≠ SyncedFingerprint  → "远端改过"
       ├ 只有一边变 → 单向推/拉
       ├ 两边都变   → 【冲突】→ 进冲突箱，挂起（不影响别的记录）
       └ 都没变     → 跳过
4. 飞书有、本地没有的 record_id      → 【飞书新建】→ 新增到本地
5. 执行所有非冲突项；冲突项留在箱子里等你
6. 写账本 sync-log.json + 更新 SyncedFingerprint
```

**幂等保证**：指纹只在**这轮真的成功写回两边之后**才更新。
所以"推到一半断网"不会丢数据 —— 下轮重新算，仍然是"本地改过"，重推一次即可（飞书侧按 record_id 更新，不会重复建）。

### 5.3 冲突箱（你选了"每次都问我"）

**关键体验设计：冲突项不阻塞其他项。**
同步非冲突的部分照常做，冲突的挂起。工具条显示 `⚠ 3 条冲突待裁决`，点开进冲突箱。

冲突箱里每一条**左右对照**：

```
┌─ 《人类简史》  ⚠ 冲突 ────────────────────────────┐
│ 字段      本地（工作台）      飞书（多维表格）      │
│ ─────────────────────────────────────────────────  │
│ 状态      在读 ←差异          已读 ←差异            │
│ 评分      5                   4      ←差异          │
│ 读完日期  —                   2026-10-01 ←差异      │
│ 标签      历史、科普          历史    ←差异         │
│ 书名      《人类简史》        《人类简史》  （相同） │
├────────────────────────────────────────────────────┤
│  [ 用本地 ]   [ 用飞书 ]   [ 两个都留 ]             │
└────────────────────────────────────────────────────┘
```

- **用本地** = 覆盖飞书那条记录
- **用飞书** = 覆盖本地（本地旧值进"历史"留底）
- **两个都留** = 飞书新建一条（用于"其实这是两本书"或"两边记的是不同版本"）

★ **默认不预选**，必须你显式点 —— 这就是"每次都问我"的正确实现。

### 5.4 删除策略（防数据丢失的核心）

| 场景 | 做法 | 为什么 |
|---|---|---|
| 你在工作台删了一条 | 本地标 `Deleted=true`（**软删**，不真删），**不推送到飞书**；清单里显示"本地已移除 · 飞书仍在" | 手滑删一下不该炸掉共享账本 |
| 飞书那边记录没了 | 本地**不自动删**，标 `RemoteMissing`，问你要不要跟着删 | 也可能是别人/你自己在飞书误删 |
| 双向自动硬删 | ★ **明确不做** | 删除是唯一不可逆的操作，而"同步"是个放大器：一次误判，两边的账一起毁 |

### 5.5 回滚与账本

- **每轮同步前自动快照** → `reading\backup\books-<时间戳>.json`（保留最近 20 份，自动轮换）
  ★ 这条来自本工程血的教训：分镜交接那个坑，最后的兜底就是"每次交接前先备份 `project.json`"。
  这里**做成自动的**，不依赖你记得。
- **每轮同步后写账本** `sync-log-<时间戳>.json`：逐条记 `record_id / 字段来源（本地还是飞书）/ 结果`。
  风格对齐 `stages\03-shot\reindex-log-<时间>.json`，**可单步撤销**。
