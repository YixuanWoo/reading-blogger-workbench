3主图为什么是「更新节奏」，不是「涨粉」

这是整件事里最要紧的一个判断

❌ 涨粉 / 播放

  • 它是结果，不是抓手
  • 今天涨得好不好，你当天改不了
  • 初创期样本少，看它容易焦虑，还看不出规律

✅ 更新节奏（今天发没发）

  • 它是你能控制的
  • 今天发没发，你今天就能改
  • 高频更新的阶段，靠的就是"不断更"

热力图长这样（示意）：

空格＝那天没发 · 越亮＝那天发得越多  |  图下面是三个读数：发了 N 支 / 落在 M 天里 / 最长连发 K 天 / 当前空档 J 天
★ 只有金色和灰色，一点红都没有 —— 红＝评判。这张图是"给自己看的诚实记录"，规矩是只陈述、不评判：不变红、不弹窗、不催你（这句话就写在卡片上）。

4四块内容，各自管什么

块管什么关键点
更新节奏热力图哪天发了、连了多久、空了几天数据只来自"每个项目的发布日"；窗口可切近 13 周 / 26 周 / 一年
账号数据卡粉丝 / 总播放 / 总点赞 / 近30天涨粉只让手填。平台口径的账号数是"拼"出来的，与其猜接口不如手填、自己负责，永远准
作品列表每支片的播放/点赞/涨粉自动从各项目 `review.json` 把多平台最新一次的数据相加；没数据就留空，不显示 0
发布日热力图的唯一原料放在项目自己的 `review.json` 里（不动 project.json）；没填就自动退回"最早那次快照的日期"，老项目一条数据都不用补

★ 一条小规矩："手填的数"和"自动算的数"不许挨着放 —— 你得一眼看出哪个是自己填的、哪个是别人替你算的。

5代码怎么拆的（回应"别过度耦合"）

拆成三层，各干各的，谁都不越界

Workbench\ Review\ ← 纯数据 / 纯算法，不知道界面长什么样 AccountReviewStore.cs 账号快照（手填数）读写 CadenceStats.cs 热力图背后的数学（连发 / 空档 / 每天几支） WorksBoard.cs 项目列表 → 作品行（自动汇总） CadenceCard.xaml(.cs) 主图卡片 Controls\ ← ★ 通用控件，完全不知道"复盘"是什么 CadenceHeatmap.xaml(.cs) 日打卡热力图（喂数据就画，换"跑步打卡"也能用） NumberField.xaml(.cs) 一个能改的数（标题 + 大数字 + 脚注） Views\ ← 只负责"把东西摆在哪儿" ReviewHostView.xaml(.cs) 容器：管"显示哪一层" + 返回条 AccountReviewView.xaml(.cs) 第一层：账号页 ReviewView.xaml(.cs) 第二层：作品页（原有）

所以你说的"以后调界面就是挪位置、改大小"，落到代码上就是：

  • 想挪哪一块 → 在 AccountReviewView.xaml 里挪那个方块（三块都是独立 Border）；
  • 想换主图 → 只改一行：_chart = new CadenceCard(); MainChartHost.Content = _chart;（换成别的图，其它文件一个字不用动）；
  • 想把热力图放到别的页面 → 那个控件不认识"复盘"，直接拿去用。

6顺手揪出并修掉的 3 个真问题

都不是"测试脚本写错了"，是软件真的有问题 —— 我点出来的

毛病为什么会这样怎么修的
点了 A 作品，进去看到的却是 B 页面顶上那个"选项目"的下拉，每次重建都会把自己选中的东西清空，然后又默认选了第一个 —— 把你刚才点的那个覆盖掉了 重建之前先记住"现在选的是谁"，填完再按它选回去
在行里改了发布日，界面看着成功了，盘上什么没写 这个格子有两个人在同时写（绑定写一次、我那段代码又写一次）。绑定先写了，我的代码再一看"值没变"就不写了 把绑定改成"只管显示"，写盘只留一个写手。教训：同一件事只能有一个写手
调试口（我点软件用的那个口）两处"不像真人" ① 读界面文字时读不到输入框里的字 → "我填的数存进去没"没法回答；② 往框里填字时不触发"离开输入框" → 那些"离开才保存"的框，字变了但根本没保存 → 会得出相反的结论 两个都补上：读字收输入框；填字时补一个"离开输入框"的动作，忠实模仿真人
