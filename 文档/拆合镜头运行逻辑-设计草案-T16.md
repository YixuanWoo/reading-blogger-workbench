## 一、问题的根子：一个镜号扛着三个身份

`ShotRow.Index` 现在同时是三样东西：

| 身份 | 谁在用 | 拆合重排后 |
|---|---|---|
| ① **顺序** | 分镜表里的第 N 个 | ✅ 跟着重排（`ReindexAndReload`） |
| ② **身份** | Agent 回填设计、渲染任务包、单镜重渲 | ❌ **不会动** |
| ③ **文件名** | `shot_007.mp4`、`shot_007.body.html`、`t_007.jpg` | ❌ **不会动** |

`ReindexAndReload()`（`Step2ShotView.xaml.cs:733`）只做一件事：

```csharp
for (int k = 0; k < _s.Shots.Count; k++) _s.Shots[k].Index = k + 1;
ReloadFromState();
```

**内存里的顺序变了，磁盘上的文件名一个没动。** 于是从拆点往后，每个镜头去读的都是隔壁镜头的画面。

## 二、现状逐条体检（都是实测）

### 拆分 `BtnSplit_Click`（`:664`）


**两个问题**：
1. **新镜一片空白** —— 没有任何设计，也不提示需要补。
2. **原镜的设计描述的是已经不存在的镜头** —— 它是为"前后半句合起来"写的（比如动效写了 `0-3s / 3-6s / 6-9s` 三段，现在这一镜只剩前 3.2 秒）。界面**不会告诉你这件事**。

### 合并 `BtnMerge_Click`（`:650`）

```csharp
a.Text = (a.Text + " " + b.Text).Trim();
a.EndSec = b.EndSec;
a.SourceEndSec = b.SourceEndSec;
a.Edited = true;
_s.Shots.RemoveAt(pos + 1);   // ★ b 的 Description / Motion / Image 随这行蒸发
```

**b 的设计静默丢失** —— 没有提示、没有备份、没有日志。Agent 生成（或你手写）的动效设计就这么没了。

### 共同问题

### 现状的真实故障场景

> 你渲完了 51 镜，成片也出了。回头觉得第 7 镜太长，拆成两镜。
> → 第 8~51 镜**全体后移一位**；磁盘上 `shot_008.mp4` 还在原地。
> → 第 9 镜去读 `shot_009.mp4` —— 那是**原第 9 镜**的画面。
> → 从第 8 镜起，**每一个镜头拿到的都是它前面那个镜头的画面**。
> → 再点「开始出片」，出来的是**整片错位**的成片，而且**没有任何报错**。
> → 而第 7 镜（合并/拆分后的）和第 8 镜（新镜）用的是原 `shot_007` / 没有产物，内容也不对。

这是"静默产出错误文件"，比崩溃危险得多。

## 三、【问题 1 的方案】运行逻辑怎么处理

### 3.1 大前提：所有交接都只走「应用到下游」（2026-10-01 13:35 用户拍板）

用户原话：

> 「现在每页好像都有应用到下游，我只有应用到下游，下游才开始标记待重渲这些。
> 所有的环节，都以『应用到下游』作为交接。回到上游修改，也是点击应用到下游，才交接、才发生变化。」

**这是整份方案的地基 —— 它把 §二 那个「静默错位」的窗口从根上关掉。**

**实测各页现状（`grep` 一遍的结果）：**

| 页 | 「应用到下游」 | 真交接？ |
|---|---|---|
| ① 粗剪页 | ✅ 有（`BtnApplyDownstream`） | ✅ **真闸门** —— 点了才让下游改用粗剪决策（`UseCoarseDecision()`） |
| 精剪页 | ✅ 有（`BtnApply`） | ✅ **真闸门** —— 点了才把精剪时间轴交出去（`FineCutKeeps = …`） |
| **② 分镜页** | ❌ **没有** | — **这正是 T-16 要补的**（现状：`SaveStageFiles()` 拆完 / 合完**立刻落盘**） |
| ④ 渲染页 | ⚠ 有（T-06 刚加） | ❌ 目前是**只读预览**（宣布源 + 算 Δ），**不是真交接** |
| ⑤ 组接页 | — | 终点，不需要 |

> ① 与精剪页共用 `ActiveDecision` 一个全局开关，顶栏有常驻显示「下游使用：精剪 · 51 段 · …」
> （`RefreshDecisionIndicator()`）。分镜页照这个模式加一份「**下游使用：镜头表 N 镜 · 已交接于 …**」。

**补上闸门之后，T-16 的结构就顺了：**

```
拆 / 合         →  只改「草稿镜头表」      下游一个字都不动
      ↓
「应用到下游」   →  才把新表推给下游        此刻才：重排 + 迁移 + 标「待重渲」
```

- 没点之前，下游读的还是**上一版已交接的镜头表** → **根本不可能错位**。
- 所以 §二 那个坑，**不是靠「迁移做得好」来解的，是靠「压根还没交接」来解的**。
  迁移（§3.5）只是把交接**那一刻**做干净 —— 它是"擦屁股"，不是"防错"。

### 3.2 给项目算一个「水位」—— 判的是「这一次交接有多贵」

不要写一堆 if，改成**给项目算一个水位**（分镜页进入时算一次，操作后更新）：

| 水位 | 名字 | 判据 | 交接的代价 |
|---|---|---|---|
| **L0** | 只有切分 | 所有镜 `Description`/`Motion`/`Image` 全空 | **无** |
| **L1** | 分镜设计已回填 | 至少一镜有设计 | 设计错配 / 丢失 → 轻确认 |
| **L2** | 已渲染 | `渲染产物\` 里有 `shot_*.mp4` | **产物要跟着改名（最麻烦）** → 强确认 + 自动迁移 |
| **L3** | 已出成片 | `stages\05-assemble\` 里有成片 | 同 L2 + 提醒成片要重拼 |

> **用户最初的原话恰好是 L0 与 L1 的分界**："镜头语义确定好之前随意拆分没问题" = L0；"已经返回了分镜设计" = L1。

### 3.2.1 摩擦分两处：拆合只问设计，闸门才摊代价

| 动作 | 弹什么 | 随水位变吗 |
|---|---|---|
| **拆 / 合**（改草稿） | 一个**只问「设计怎么处理」的轻框**（两选项，见 §3.3）；设计全空（L0）时**不弹** | ❌ **不变** —— 这是草稿内的事，跟下游无关 |
| **点「应用到下游」** | 后果预览 + 代价：L0/L1 轻确认；L2/L3 **红字 + 具体产物数** + 自动迁移 + 勾「我知道画面会失效」 | ✅ **按水位** |

**关键取舍**：不要在 L2 **禁止**拆合。用户灵感来了的时候被系统拦住，比让他确认一次更烦。要做的是**把代价说清楚 + 自动擦屁股**。

★ **水位决定的"贵"，从「拆的那一刻」移到了「交接的那一刻」** —— 这是本方案相比初稿最重要的结构调整：
初稿把强确认挂在拆分按钮上（拆的时候就拦你），现在挂在「应用到下游」上（拆随便拆，交棒才拦）。
这既兑现了用户说的"随意拆分没问题"，又保证下游永远只吃已交接的版本。

### 3.3 设计数据的处理（P1 / P2 / P3）

**拆分时 —— 只有两个选项**（2026-10-01 13:35 用户澄清，原稿的三个选项是错的）：

| 选项 | 含义 |
|---|---|
| **① 保留原镜设计**（默认） | 原镜（前半）设计**全文保留**，打 `DesignStale` → 「待复核」；新镜（后半）**置空** → 「待补设计」 |
| **② 彻底清空重新设计** | 两镜的设计都清空 → 都标「待补设计」，交给 Agent 重做 |

★ **为什么删掉「按时间自动切分」这个选项**（用户原话）：

> 「本身镜头的组成单元就是转写好的句子，已经自带时间了。拆镜头必然就是按时间自动切分。
> 怎么还会需要这个选项？这里应该选的就是保留原来的设计，或者彻底清空重新设计。」

用户说得对 —— 那个选项把**两件事混成了一件**：

- 「**时间**怎么切」= 必然，且唯一（镜头单元就是句子，句子自带起止时间）→ **不是选项，是定义**；
- 「**设计**怎么办」= 才是真需要用户拍板的（设计是自由文本，跟不跟着走）。

原稿还把「自动切分」描述成"写得规整才切得动"（要 `0-3s/3-6s` 那种格式），
这恰恰暴露了它是个伪选项：**能不能自动切，取决于当初怎么写，而不取决于用户现在想怎样** —— 这种选项不该摆给用户。

**合并时**（改掉现在的静默丢弃）：

| 时机 | 处理 |
|---|---|
| **默认：两段拼接** | `a.Description + "\n" + b.Description`（`Motion` / `Image` 同理） |
| 合并后 | 打 `DesignStale` → 显示「待复核」 |

**为什么拼接是合理的**：合并后这一镜的内容**确实就是 a、b 两段连续的**，所以 a 的设计 + b 的设计拼起来恰好覆盖了新范围（只是时间轴要重基）。这比"只留一个、丢掉另一个"更不丢信息，也比弹窗让用户选更省事——用户看到不合适的直接删掉后半段就行。

**`DesignStale` 怎么清**：用户在卡片上点「确认无误」即清掉。**不自动清**（自动清等于系统替用户判断，正是现状的毛病）。

### 3.4 镜号与产物（P4 / P5）★ 本方案的核心

> **2026-10-01 12:55 用户提出两个方案，本节据此重写。**
>
> - **用户方案 1**：拆一镜，后面镜号顺推 +1 —— **分镜设计也跟着顺推 +1**。
> - **用户方案 2**：镜号随拆合变化，但**每个镜头另有一个独立 ID，镜号变、ID 不变**。
>   分镜设计永远跟着 ID 走，不跟着镜号走。

#### 3.4.1 先纠正一个前提：这两个方案不是二选一

| | 管什么 | 谁在用 |
|---|---|---|
| **镜号**（顺推） | 「排第几」「叫什么名字」 | 界面显示、`shot_NNN.mp4` 文件名、Agent 提示词、组接页块序、人嘴里的"第 7 镜重渲一下" |
| **ID**（不变） | 「这份设计 / 这个产物是谁的」 | 分镜设计归属、渲染产物归属、留痕文件、撤销、对账 |

**它们是同一件事的两半，不是两个方案。**

- 只有顺推、没有 ID = **蒙着眼睛搬 44 个文件**，搬错了不知道（正是现状的病）。
- 有 ID 的顺推 = 有清单、能校验、能回滚、能撤销。

**所以推荐：顺推（方案 1）当主干，ID（方案 2）当内核 —— 两个都要，合起来才成立。**

★ 顺带改进：原先设想的 α 是「镜号变成 7a/7b」（镜号本身不连续了，界面会变形）。
用户的方案 2 是「**镜号照样连续顺推，ID 藏在后面**」—— 界面完全不变，思路更好，**采纳**。

#### 3.4.2 真正要选的是这个岔路：磁盘上的文件动不动

有了 ID 之后，还剩一个问题必须回答：**`shot_007.mp4` 这个名字，跟不跟镜号走？**

| | **甲 · 文件跟着改名（推荐）** | **乙 · 文件名按 ID，磁盘永不动** |
|---|---|---|
| 文件名 | `shot_007.mp4`（= 当前镜号） | `shot_<ID>.mp4`（永不变） |
| 拆一镜时 | 从拆点往后 N 个文件改名 | **零磁盘操作** |
| 人的可读性 | ★★★ 目录里一眼对上镜号 | ★ 看目录不认识，得查表 |
| 下游改动 | **零**（渲染页 / 组接页 / 提示词照旧） | 4 处要改（命名规则 + 解析 + 提示词 + 组接块序） |
| 老项目迁移 | 拆合时才动 | 要一次性把 51 个文件改名 + 建清单 |
| 出错风险 | 有（N 个文件搬一半）→ 靠**计划 + 校验 + 回滚**压住 | **无**（不碰磁盘 = 不会半途而废） |
| 人工排查 | 直观 | 费劲（"第 9 镜的产物怎么叫 shot_007？"） |

**推荐甲**：下游零改动 + 目录可读 + 风险用 ID 对账压得住。
（乙 唯一的优势是"零磁盘风险"，代价是**人看不懂目录** —— 而这个软件的日常维护恰恰常靠人翻目录。）

**先做 ID 的好处**：它给未来留了门。哪天觉得"搬文件"烦或怕，切乙只需改「命名 + 解析」这一层，
**数据层一行不用动**。

#### 3.4.3 算法骨架

```
拆 #k 成两镜：

① 原镜 k          ID 不变，Index 不变，DesignStale = true（挂「待复核」）
② 新镜插入 k+1    分配新 ID，设计字段全空（挂「待补设计」）
③ k+1 之后的镜头   镜号 += 1，ID 全不变
④ 算搬迁计划      [ { id:"s07", from:"shot_007.mp4", to:"shot_008.mp4" }, … ]
⑤ 执行            按"安全顺序"（见细节 1）
⑥ 校验            按 ID + 指纹逐条核对
⑦ 收尾            全成功 → 删计划文件；任一失败 → 按计划反向回滚，恢复原状

合并 #k, #k+1：
  ① 保留靠前那个（k）的 ID；k+1 的 ID 记进 mergedInto 后作废
  ② k 之后的镜号 -= 1
  ③ ④~⑦ 同上
```

**三个必须做对的细节（这才是"算法"里最容易翻车的地方）：**

**★ 细节 1：改名必须倒序（或双缓冲），否则自己覆盖自己**

拆镜是"镜号变大"，若从前往后搬：`shot_008.mp4 → shot_009.mp4` 会**盖掉还没搬的 `shot_009.mp4`**，
那个文件的原内容就**永久丢了**。

| 操作 | 镜号怎么变 | 安全顺序 |
|---|---|---|
| 拆分 / 插入 | 变大（+1） | **从大号往小号搬** |
| 删除 / 合并 | 变小（−1） | **从小号往大号搬** |
| 图省事 | —— | 全部先改 `*.tmp`，搬完再统一改回正式名（**双缓冲，永不覆盖**） |

**★ 细节 2：ID 里绝对不要带镜号**

用户举例的 `123a` 不行 —— 镜号一变，`123` 就成了**撒谎的历史遗迹**
（同一个 ID 迁移完挂到了别的序号上，看 ID 反而误导）。

**建议 ID 格式：与位置无关的递增短码**，如 `s01`、`s02` …（立项 / 切分时发号，永不复用）。
血缘另记两个字段：新镜记 `fromId`（从谁拆出来的），老镜记 `mergedInto`（被并到哪去了）。
这样「它是谁」和「它从哪来」是两件事，各自都不会撒谎。

**★ 细节 3：只改「驱动流程」的文件，不动「留痕」的文件**

- ✅ 改：`shot-NNN.*` 各种产物、`shot-overrides.json`、`render-tasks.json`
- ❌ **不动**：`agent-response.json`、`prompt.md`、`apply-preview.json`、`render-verify.md`
  —— 它们是"当时发生了什么"的记录。**留痕文件里带上 ID 就够了**：镜号后来变了，靠 ID 照样对得上，一个字不用改。

#### 3.4.4 ID 什么时候发？（老项目怎么办）

- **新项目**：切分（出镜头表）时一次性发号，之后只增不改。
- **老项目**（如 `思辨与立场` 51 镜）：**补发一次** —— 按当前顺序 1..51 各发一个 ID，写进 `shotlist.json`。
  这一步**不改任何文件名、不动任何产物**，纯加字段，做完一次永不回头。
- **迁移清单**（拆第 7 镜 → 原 8..51 后移为 9..52）：

```
① 项目\<名>\渲染产物\shot_NNN.mp4          → shot_(NNN+1).mp4
② 项目\<名>\渲染产物\shot_NNN.prev.mp4     → shot_(NNN+1).prev.mp4
③ 项目\<名>\渲染工作区\bodies\shot_NNN.body.html → shot_(NNN+1).body.html
④ stages\04-render\thumbs\t_NNN.jpg        → t_(NNN+1).jpg
⑤ stages\04-render\shot-overrides.json     → notes 字典的键跟着改
⑥ stages\04-render\render-tasks.json       → 整份按新分镜表重新生成
⑦ stages\03-shot\shotlist.json / images.json → SaveStageFiles 已自动重写 ✅
```

**只改「驱动流程」的文件，不改「留痕」的文件**：

- ✅ 要改：`shot-NNN.*` 各种产物、`shot-overrides.json`、`render-tasks.json`

**迁移必须可回滚**：

3. 失败中断 → 按日志反向回滚
4. 成功后日志留档（这也是"事后能查为什么文件叫这个名"的唯一依据）

#### 3.4.5 ID 的作用范围：藏后台 ≠ 只在上游（2026-10-01 13:08 用户追问）

用户的理解：

> 「下游渲染出来的视频就按镜号命名，别管 ID。ID 只是为了让分镜设计和镜头保持一致、一直有挂钩。
> 但是我已经进入渲染环节的话，就不存在这个问题了嘛。ID 永远藏在后台就行了。
> 还没点渲染时，上游有改动，镜头列表往下推，推到下游按镜头号渲染，这不就不会有错嘛。」

**前半句完全采纳，后半句要补一刀。**

| 用户的话 | 判定 | 说明 |
|---|---|---|
| 产物按镜号命名 | ✅ 对 | 就是 §3.4.2 的「甲」 |
| ID 不写进文件名 | ✅ 对 | ID 只做归属与对账，不参与命名 |
| 还没点渲染时随便改 | ✅ 对 | 就是 L0 / L1，本来就不打扰 |
| **「进了渲染环节就不存在这个问题」** | ⚠ **要补** | 准确说是「**重新渲染完**」才没有 —— 中间有个窗口 |

**那个窗口长什么样：**

1. 51 镜全渲好（磁盘上是 `shot_001..051.mp4`，都是**旧镜头表**的产物）
2. 回分镜页拆第 3 镜 → 镜头表变成 52 镜
3. **此时磁盘一个文件都没动**：`shot_004.mp4` 还是「旧第 4 镜」的画面，
   可第 4 位现在坐的是「原第 3 镜的后半」
4. 这时候去 ⑤ 组接页出片 → 按镜号读 → **整片错位，且不报错**

**★ 关键区分：「改名」和「重渲」是两件事**

用户说「下游按镜头号渲染就不会错」—— **对，但前提是「全部重渲」**。而拆一镜之后：

- 除了拆点那一两镜，**其余 40 多个镜头的画面内容一模一样**
  （第 5 位装的就是原第 4 镜的画面，一帧都没变）
- 所以**根本不需要重渲，只需要改个名字** —— rename 是毫秒级；重渲 52 镜是十几分钟 + 电费

**这就是「甲」方案的全部价值：不重渲，只改名。**

**那 ID 在这里干什么（回答「藏后台就行」）：**

- ID **不参与命名** ✅（用户说的对）—— 但它也不能只活在上游
- 因为：渲染页现在只会看「文件在不在」→ `shot_004.mp4` 在 → 报「已渲染」→ **其实是旧内容**
- 有了 ID → 能算出「第 4 位现在是 `s03b`，而磁盘上 `shot_004.mp4` 的归属是 `s04`」→ ⚠ **产物已过期**

**一句话：ID 不上门牌，但入住要刷它。藏后台 ≠ 只在上游。**
最低要求：**ID 要活到渲染页**（写进 `render-manifest.json`），组接页才能拦得住错片。

### 3.5 产物有效性：新增「渲染清单」（建议一并做）

光迁移文件名还不够 —— 迁移完，那个 `shot_007.mp4` 到底还是不是"当前第 7 镜"的产物？需要一份对账依据。

新增 `项目\<名>\渲染产物\render-manifest.json`：

```json
{
  "s07": {                                   // ← 键是永久 ID，不是镜号
    "shot": 7,                               // 渲染那一刻的镜号（仅供人看，会过期）
    "renderedAt": "2026-09-30T15:58:40+08:00",
    "fingerprint": "sha1(台词|画面构思|动效|配图|时长)",
    "file": "shot_007.mp4"
  }
}
```

★ **键必须是 ID**。如果键写成 `shot_007`，那拆合改名后这份清单自己就过期了 ——
用 ID 当键，镜号怎么变，这份清单永远是对得上的（`file` 字段跟着迁移一起改）。

有了它，**任何一处都能一眼判断**：

| 情况 | 状态 | 徽章 |
|---|---|---|
| 有产物 + 指纹一致 | 已就绪 | 绿 |
| 有产物 + 指纹对不上（改过文案/设计，或拆合导致） | 内容已变，待重渲 | 红 |
| 没有产物 | 待渲染 | 灰 |
| 没产物 + 需要设计 | 待渲染 + 待补设计 | 灰 |

**这一份顺便把另外两个老问题的根也拔了**：
- ④ 渲染页的"状态"列现在只看"文件在不在"，有了指纹就能说"这份产物是旧的"；
- 改了台词/设计后，能立刻知道哪些镜需要重渲（现在完全靠人记）。

### 3.6 Agent 并发保护（P6）

`FillVisuals` 按 `Index` 回填。如果用户在 Agent 跑的过程中拆了镜头，回填就会错位。

**处理**：拆合操作时，如果 Agent 正在跑（`_busy == true`）→ **禁止**，提示"等这次设计跑完再调"。
再加一道保险：任务包里带上**启动时的镜头指纹**，回填时若发现当前镜头表已变 → **拒绝回填**，提示"镜头表在这次设计期间被改过，这份设计已作废，请重跑"。

### 3.7 重切分（`BtnResplit`）

现状：有 `Edited` 镜时弹确认，然后整表重切。

**新逻辑**：水位 ≥ L1 时，确认框升级 —— 不只说"手动调过的会被覆盖"，还要说**"51 镜的分镜设计会全部清空"**（重切是重建镜头表，设计字段全丢）。L2 以上再加"渲染产物全部作废"。

## 四、【问题 2 的方案】拆 / 合的 UI 怎么显示

### 4.1 操作前 —— 两个框，各管各的

按 §3.2.1 的分工，UI 上是**两个完全不同的框**，别合并。

#### 框 A：拆 / 合时（只问设计，**不摊代价**）

设计全空（L0）时**不弹**，直接拆 —— 兑现"随意拆分没问题"。

```
│  把第 7 镜拆成两镜？                                  │
├──────────────────────────────────────────────────────┤
│  这一镜已经有分镜设计，拆开后它会变成：                │   ← 变化预览

│  原来的设计怎么办？                                  │   ← 唯一的选择项（两选项）
```

> ★ **这里没有"多少产物要改名"那行** —— 因为拆完**下游一个字都不动**（§3.1），
> 代价要等你点「应用到下游」时才发生、才需要说。放这里就是吓唬人。

1. **主角是"后果预览"，不是"你确定吗"** —— 把 `#7 / #8` 拆开后会变成什么直接摆出来。
2. **只有一个选择项**，就两个选项（保留 / 清空）。别再塞第三个（见 §3.3 为什么删掉"自动切分"）。

```
│  ┌────────────────────────────────────────────────┐  │

│  │ #8  原设计不会丢，拼进合并后的第 7 镜            │  │
```

```
└──────────────────────────────────────────────────────┘
```

| 水位 | 框 B 长什么样 |
|---|---|
| **L0** | 一行轻提示即可（"已交接"，无代价） |

| **L3** | 同 L2 + "成片需重新组接" |

**L2 及以上的勾选**（"我知道…会失效"）是防手滑连点 —— **挂在这个框，不是挂在拆合框**。

### 4.2 操作后：卡片上的状态徽章 + 顶部汇总条

**卡片**（T-15 的卡片流；若 T-15 未做，同样的徽章画在表格的「状态」列）：

```
┌──────────────────────────────────────────────────────┐
│ ▌#7  ✎  0:00 → 3.2s   [待复核]  ⚠ 设计可能已不覆盖…  │  ← 橙边条
│ ▌#8       3.2s → 7.4s [待补设计]  [只补这一镜]       │  ← 灰边条 + 快捷按钮
└──────────────────────────────────────────────────────┘
```

**状态徽章全表**：

| 徽章 | 颜色 | 含义 | 出现时机 |
|---|---|---|---|
| `待复核` | 橙 `Warn` | 设计可能已不覆盖当前范围 | 拆 / 合之后；用户点「确认无误」清除 |
| `待补设计` | 灰 `TextDim` | 这一镜没有任何设计 | 拆分产生的新镜 |
| `待渲染` | 灰 | 没有产物 | 新建镜 / 产物被作废 |
| `待重渲` | 红 `Danger` | 有产物，但内容已变（指纹对不上） | 拆合 / 改了文案设计 |
| `已就绪` | 绿 `Ok` | 有产物且内容一致 | 正常态 |
| `✎` | 橙 | 手动调过边界（**保留现有语义，不合并到上面**） | 拆 / 合 / 改边界 |

> `✎`（边界被调过）和设计状态（`待复核`）是**两件事**，不要合并成一个标记 —— 一个是"重切分时别覆盖我"，一个是"我的设计要复核"，清掉的条件不同。

**顶部汇总条**（操作后出现在分镜区顶部，可关）：

```
本次拆合：1 镜设计待复核 · 44 个产物已改名 · 1 镜待渲染        [撤销这次拆合]  [知道了]
```

### 4.3 撤销（建议做，单步就够）

拆合是破坏性操作，而现在**没有任何撤销**。做一个**单步撤销**性价比最高：

- 执行前把 `_s.Shots` 深拷贝一份快照 + 记录产物迁移日志
- 撤销 = 恢复 shotlist + 反向改名文件
- **只保留最近一次**（不做多步栈，复杂度不值）
- 页面重载 / 切换项目后失效

### 4.4 顺手要改的两个现有提示（都是"说错话"）

1. **`RefreshEditButtons` 的按钮可用性**（`:737`）—— L2 以上，「拆分/合并」按钮旁挂一个橙色小点，鼠标悬停说明"会影响 44 个渲染产物"。
2. **`TxtEditHint`**（`⚠ N 镜手动调过，重切会覆盖`）—— 水位 ≥ L1 时补充文案："另有 N 镜已有分镜设计，重切会清空"。

## 附：一句话总结

**现状是「改内存、不改磁盘」，而且一个镜号当了三个身份用。**

T-16 做的是一条链：

```
① 拆 / 合只改草稿（随便拆，不打扰）

```

★ 关键认识：那个「产物静默错位」的坑，**不是靠"迁移做得好"来解的，是靠"没点交接就压根没生效"来解的**。
迁移只是把交接**那一刻**做干净。
