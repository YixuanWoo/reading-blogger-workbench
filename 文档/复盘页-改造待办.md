## 2. 要变成什么样（目标形态）

### 2.1 两种复盘，各管一摊

| | **账号复盘（第一层）** | **项目复盘（第二层）** |
|---|---|---|
| 关注什么 | **整个账号的增量水平** | **每一条视频的数据** |
| 一行是什么 | 一张卡片上的 4 个数；曲线上一段时间一个点 | 一支片（账号页列表里一行）／一次快照（作品页里一行） |
| 回答的问题 | 我这个号在涨、在平、还是在掉 | 这条为什么行 / 为什么不行 |
| 数据粒度 | 粉丝总量、总播放、总点赞、月度涨粉… | 播放/完播/点赞/涨粉/收藏… 逐条 |
| 数据来源 | ★ 需要**新的数据**（手填 + 汇总，见 §3①） | 项目自己的 `review.json`（已有） |
| 天然的时间轴 | **有**（账号是随时间累积的） | 无（一条一条看） |

### 2.2 页面形态（★ 2026-10-15 定案：**一层套一层**）

> **取代原来"两个标签页"的方案。** 用户拍板的方向 —— 跟抖音创作者中心一样：
> 上面账号数据，下面作品列表，点进去看作品数据。

```
┌─ 复盘（一级）─────────────────────────────────────────┐
│  ①账号页                                    [平台 ▾]  │
│                                                       │
│   ★ 主图：更新节奏（近 26 周热力图 · 一天一格）        │
│     ░█░█░░██░█░██░░█░██░█░░██░█░██░█░░█░██░█          │
│     近 26 周发 54 支 · 最长连发 9 天 · 当前空档 2 天   │
│     ※ 全自动，不用你填一个字                          │
│   ─────────────────────────────────────────────────   │
│   ┌────────┬────────┬────────┬────────┐               │
│   │ 粉丝总量│ 总播放 │ 总点赞 │近30天涨粉│ ← 手填(次要)  │
│   └────────┴────────┴────────┴────────┘               │
│   ※ 手填的与自动算的必须分开摆，绝不并排               │
│   ─────────────────────────────────────────────────   │
│   作品          发布日   播放    点赞   涨粉   状态    │
│   ▸ 思辨与立场   09-20   12.3万  891   +42   已归档    │
│   ▸ AI时代读书…  10-02    3.1万  156   +12   进行中    │
│   ▸ 达克效应…    10-11     —      —     —    待填数据  │
│          │                                            │
│          └─ 点某一行 ↓（钻进这支片）                   │
│  ②作品页： [← 返回账号]  作品：思辨与立场              │
│      ┌ 录入表单（平台/发布日/统计日/天数 + 8 个数 + 三段结论）┐
│      ├ 已有快照列表（点中载回表单改 / 删除）            ┤
│      └ [保存为新快照]  [生成复盘报告.md]               ┘
└───────────────────────────────────────────────────────┘
```

**为什么这个比"两个标签页"好**：
- 更贴直觉 —— 就是"总览 → 点进去看详情"，不用先想"我该点哪个标签"；
- 原来担心的"两种数据混在一屏分不清"**其实不成立** —— 账号那几个数是**卡片**（不是列表），
  下面那个是**唯一的一份列表**，不会打架；
- 顺手多出一个好处：**没填过数据的片子会在列表里显示「待填数据」**，
  复盘待办自己就浮出来了。

**唯一的新增**：主图（更新节奏）＋ 账号数据卡 ＋ 它的历史（将来画曲线用）。
作品列表和作品页**都是现成的**：
列表 = 项目列表（`ProjectStore.LoadAll()`），数字 = 读各项目 `review.json` 的最新快照，
作品页 = 现在这个 `ReviewView`（只加一个「← 返回」）。

### 2.3 ★ 首页主图 = 「更新节奏」

> **2026-10-15 晚定案。** 用户问"初创阶段账号数据里什么最重要，把最重要的做成可视化放最显眼处"。

**定案：主图放「更新节奏」—— 一张日打卡热力图（近 26 周，一天一格），出了片就点亮，断更就是空格。**

**为什么不是涨粉 / 播放 / 粉丝总量**（四条理由，按分量排）：

| # | 理由 |
|---|---|
| ① | **主图该放"别处看不到"的东西。** 涨粉、播放这些数，钻进任何一支片的详情页都能看到来源；而"我最近几周有没有在稳定出片"**只存在于账号页**。这个位置太贵，不能浪费在重复信息上 |
| ② | **它是唯一 100% 由你控制的变量。** 涨粉是结果、滞后、还带运气；更新是原因、立刻、只看自己。初创期盯结果会崩，盯原因能活下来 |
| ③ | **它零手填。** 从各作品的**发布日**算出来。这条直接把 §6 里最大的那条风险（"手填坚持不下来"）从主图上删掉了 |
| ④ | **样本量的现实。** 初创期只有几支片，一趟涨粉曲线就是几个 0 之间的抖动，看的是噪声，只会让人泄气 |

**图上要带的三个数**（都由同一条数据算出来）：
`近 N 周发了 X 支` · `最长连发 Y 周` · `当前已空 Z 周`

★ **说话的口气（硬规矩）**：只陈述、不评判。**不变红、不弹窗、不催**。
这句话是**指南针，不是监工** —— 一旦它开始催人，人就会开始讨厌打开这一页，这功能就废了（进 §6 风险表）。

★ **主图可换（阶段自适应）**：不是永远画这张。到第二阶段样本够了，
主图位置换成「哪一类内容行」（播放/完播分布），第三阶段再换成涨粉曲线。
所以主图区做成**可换内容**，别死写一张图。

| 你在哪 | 主图该看什么 |
|---|---|
| **0～10 支片（现在）** | ★ **更新节奏** —— 样本太小，涨粉全是噪声 |
| 10～30 支 | 「哪一类内容行」—— 播放/完播的分布，这时才有规律可看 |
| 30 支以上 | **涨粉速度曲线** —— 到这时它才有统计意义 |

**唯一的数据依赖 = 发布日。** 所以要把录入成本压到最低：
- 作品列表**那一行上直接可改日期**（不必进详情页填表）；
- 再加一个**一键「已发布」按钮**（点一下记今天）。
  热力图是**天**粒度，但"哪天算哪天"不较真（发布日填错一天不影响总体形状）。

★ **它具体长什么样（日打卡热力图）见 §2.4** —— 形态已定，B1 照它实现。

### 2.4 ★ 主图的视觉样式（★ 2026-10-15 深夜**改定**，B1 照这个做）

**样式名：日打卡热力图**（GitHub 贡献图 / 打卡秘籍 同款）。

> **为什么改主意**：我原先推的是"周打卡条、一格一周"，理由是"初创期片子少，
> 一天一格会大片空着、看着挫败"。**用户当场推翻了这条假设** ——
> 明确说未来会**高频更新**（一周多更，还要往更密的节奏冲）。
> 假设一翻，热力图的短板（稀疏）就没了，长板（**一眼看半年的连续性**）全出来了。

```
┌─ 更新节奏 ───────────────────── 少 ▢▢▢ 多 ─┐
│  近 26 周 · 一天一格 · 颜色越深，当天发得越多 │
│  一 ┌───────────────────────────────────┐ 4月 │
│  三 │  ▢ 格 格   格  格 格  格 格 格    │ 5月 │
│  五 │   格 ▢ 格 ▢ 格 ▢ 格 格 ▢ 格 ▢     │ 6月 │
│      │  ▢ 格 格 格 ▢ 格 格 ▢ 格 格 格 ▢  │ ... │
│      └───────────────────────────────────┘10月 │
├───────────────┬───────────────┬──────────────┤
│     54 支     │      9 天     │      2 天    │
│  近 26 周发布 │   最长连发    │    当前空档   │
├───────────────┴───────────────┴──────────────┤
│  它只陈述，不评判 —— 不变红、不弹窗、不催你。 │
└──────────────────────────────────────────────┘
（一列 = 一周；一行 = 星期几；虚线圆框 = 今天那一格）
```

**怎么读它（四件事一次看懂）**：

| 视觉元素 | 说的是什么 |
|---|---|
| **一行 = 星期几，一列 = 一周** | 熟悉热力图的人零学习成本；新人看一眼"竖的条纹"就懂了 |
| 格子的**亮 / 暗** | 当天有没有出片 |
| 颜色**深浅**（浅金 → 深金） | 当天发了几支 —— 给"一周多更"准备的 |
| **虚线圆框那一格** | 今天（还没发就是空着的） |
| 连续的**亮格长条** | 连发 —— "最长连发 9 天"是**数出来**的，不是被告知的 |

**读数全部改成「天」粒度**（热力图是日粒度，读数跟着走，否则上下对不上）：
`近 26 周发布 N 支` · `最长连发 Y 天` · `当前空档 Z 天`

**★ 铁律照旧**：只有两种色系（金 = 发了 / 浅灰 = 没发），**刻意不用红色** ——
红色是"评判"，跟"只陈述不评判"的口气直接冲突。断更就是几个浅灰格子静静地在那儿。

**时间窗**：默认 **近 26 周（半年）**，可切 `近 13 周` / `近一年`。
26 周是**刻意的起点** —— 新号攒不满一年，左边会空一大块；26 周刚好铺满且格子够大。
★ 实现时**格子尺寸随窗口宽度自算**（`格宽 = (可用宽 - 间隔×(列数-1)) / 列数`），
所以加"近一年"不用改样式，只改列数。

**配色（浅色设计稿 / 深色工作台实际，实现按当前主题取）**：

| 用途 | 浅色（设计稿） | 深色（工作台实际） |
|---|---|---|
| 卡片底 | `#FFFFFF` ／描边 `#D3D1C7` | `#12151A` ／描边 `#2A2F38` |
| 没发（格） | `#F1EFE8` | `#1B1F26` |
| 发了 1 支 | `#FAC775` | `#6B4E17` |
| 发了 2 支以上 | `#EF9F27` | `#C99A2E` |
| 虚线圈（今天） | 描边 `#888780` | 描边 `#9A9890` |
| 主文字 | `#2C2C2A` | `#E8E6E1` |
| 次文字 | `#5F5E5A` / `#888780` | `#9A9890` / `#6E6C66` |

★ **深色下"深浅"是反的**（深底上越亮 = 越多），实现时别直接搬浅色那三档。

**备选（已否）**：

| 样式 | 为什么不用 |
|---|---|
| 周打卡条（一格一周，先前我的推荐） | 格子太粗，**看不出是"哪天"断的**；而且它跟热力图比没多出什么信息 |
| 周柱状（一周一根柱） | 柱高要"一周多更"才有意义；且**像报表，没有打卡感** |
| 只用文字 | 没有形状，看不出断在哪 |

**★ 以后可以长成什么样（先记着，B1 不做）**：
格子颜色现在是"当天发了几支"。等作品数据攒起来，可以**把颜色换成"当天发布的作品播放量"** ——
那就从"打卡图"升级成"**内容绩效图**"：一眼看出哪几天发的片爆了。字段不用新加，`review.json` 里就有。

**还没定的小事**（B1 随手定）：点一格要不要跳到那天发的作品；悬停要不要出小卡片（"10-02 · 2 支"）。

## 3. 七条设计判断（★ 2026-10-15 晚定案）

> ①②③④ 原为"开工前必须拍板"，2026-10-15 晚已连同形态一起拍完。
> ⑤⑥ 是定案"一层套一层"之后**新冒出来**的两条；⑦ 是"主图放什么"。

| # | 定什么 | **定案** | 为什么 |
|---|---|---|---|
| ① | **账号级数据从哪来** | **手填 4 个数**（粉丝总量 / 总播放 / 总点赞 / 近 30 天涨粉）＋**列表数字自动汇总**，**两者分开摆、绝不并排** | 粉丝总量、账号总播放这类数**项目里根本没有**，工作台算不出来，只能手填。而"列表里的播放"能把各作品加起来。★ 但"抄来的"和"算出来的"**绝不能并排当同一回事** —— 工程老规矩（写作台的预估时长就吃过这个亏） |
| ② | **账号复盘的横轴** | **时间（周 / 月）** | 账号的"增量"是按时间累积的，横轴只能是时间 |
| ③ | **账号数据落哪** | **`%APPDATA%\翊瑄的工作台\account-review.json`** | 账号是**所有项目的总和**，挂在任何一个项目底下都不对。放 AppData 里跟项目解耦，随时能填 |
| ④ | **汇总算不算已归档的** | **算** | 已归档的片子数据还在本地（`<项目>\review\` 就是为这个留的）。不算的话账号复盘会凭空少一块 |
| ⑤ | **平台维度怎么摆** | **顶部加「平台 ▾」筛选，默认"全部"** | 严格说"账号"=**某个平台上的号**（抖音号/小红书号/B站号是三个号，粉丝数各是各的）。数据的 `Platform` 字段**本来就有**，直接用。只做一个平台时它就一直显示"全部"，等于不存在 |
| ⑥ | **列表一行代表什么 + 合计口径** | **一行 = 一支片**（多平台合并）｜合计规则：**每个平台各取它最新的那一份快照，再加起来**｜**只摆能相加的数**（播放/点赞/涨粉），**完播率不进列表** | 跟抖音"作品列表"一个意思，用户一眼就懂。完播率是比率、加不了，硬加就是编数，所以它只出现在作品页里 |
| ⑦ | **首页最显眼处放什么** | **主图 = 「更新节奏」**（近 26 周日打卡热力图，全自动） | 主图该放**别处看不到**的信息（涨粉/播放在作品页都有）；节奏是唯一 100% 由自己控制的变量，且零手填。详见 §2.3 |

**由 ⑥ 顺带得到的两个副产品**（不用额外干活，白捡）：
- 列表里没数据的片子显示「**待填数据**」→ 复盘待办自动浮出来；
- 一行上面挂平台小标签（如"抖音+视频号"）→ 一眼看出这支片发了几处。

## 4. 数据放哪（关键，先说清免返工）

```
项目复盘（已有，不动）
  <项目>\review\review.json         ← 逐条视频 × 多平台 × 多次快照
  <项目>\review\复盘报告.md          ← 人读的那份

账号复盘（拟新增，形态已定）
  %APPDATA%\翊瑄的工作台\account-review.json
     └─ 一条 = 某平台在某一天的一次"账号快照"（跟项目快照同一个套路）
          platform     平台（抖音 / 视频号 / …）
          statsDate    统计日
          fans         粉丝总量        ← 手填
          totalPlay    总播放          ← 手填
          totalLike    总点赞          ← 手填
          fans30d      近30天涨粉       ← 手填
          note         备注（可选）

  作品列表的数字：不存盘，每次现算 ——
     扫所有项目的 review.json，每平台各取最新快照，加起来。
     （只读小 json，几十个项目也就几十毫秒；结果可缓存）
```

★ **两条铁律照旧适用**：
- 写盘一律**无 BOM**（R-13）；
- 加字段 = 安全（老档案读到默认值），所以 `account-review.json` 加字段不用改结构版本。

★ **和归档的关系**：跟项目复盘同一条规矩 —— **完全解耦**，随时能填，不必等硬盘插着。

## 5. 分期与代价（建议顺序）

| 期 | 做什么 | 规模 | 依赖 | 状态 |
|---|---|---|---|---|
| **A** | 一级页 + 项目选择器（现在这套） | ~80 行 | 零 | ✅ **V1.14.0** |
| **B1** | **账号页**：★ 主图「更新节奏」热力图 ＋ 手填 4 数数据卡 ＋ 作品列表（自动汇总 + 行内改发布日）＋ 点一行钻进作品页 | 大（~500 行） | ③⑤⑥⑦ 已定案 | ✅ **V1.15.0** |
| **B2** | **账号历史**：账号快照按时间录入 + 折线（"在涨还是在平"） | 中（~300 行） | B1 | ⬜ |
| **C** | 跨项目排行 / 筛选增强（B1 的列表已经吃掉一大半） | 小（~150 行） | B1 | ⬜ |
| **D** | 图表（老方案的 R2：折线 / 横向条 / 对比柱，WPF 手绘不引库） | 中（~450 行） | A | ⬜ |

★ **建议顺序：B1 → D → B2 → C**。
理由：**B1 是这一整轮改造的"门面"** —— 打开复盘第一眼就是它，
而且它**几乎全是复用**（项目列表 + 各项目 review.json + 现在的 ReviewView），
新增的只有"账号卡 + 汇总 + 返回按钮"三样。
D（图表）紧跟其后，因为 B1 的列表一旦有数字，人立刻就会想"能不能排个序、看个条"。
B2/C 放最后 —— **"我这个号在涨还是在平"比"全项目排行"有用得多**，
而排行样本不到 5~8 支片时是噪声（老方案已论证过）。

⚠️ **B1 最大的坑不是画图，是"手填坚持不下来"**：
粉丝总量这类数，你隔三差五要回去抄一次。所以设计的第一原则是
**能自动汇总的一律不让手填**，手填的字段**压到 4 个以内**（现在定的就是 4 个）。

## 6. 风险登记（拟，定案后编号进 `优化与风险登记.md`）

| 拟号 | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R-拟 | **主图变成"监工"，让人开始讨厌打开复盘页**（★ 新，分量最重） | 高 | 只陈述不评判：**不变红、不弹窗、不催、不用"目标/落后/加油"这类话术**；断更就静静显示空格 |
| R-拟 | **发布日没人记 → 主图长期空着** | 高 | 作品列表**行内直接改日期** ＋ 一键「已发布」按钮记今天；**周粒度容错一天**；没记录的日子只是空格，**不报错、不提示** |
| R-拟 | **账号数据手填坚持不下来** | 中（↓ 主图已零手填，风险面缩小） | 能算的绝不让填；手填字段 ≤ 4 个；**不填也不影响主图**；不催（没到点不提示） |
| R-拟 | **两种数被人当成一回事**（把"列表汇总"当成"平台显示的账号总量"） | 高 | 卡片和列表**物理分开**（卡片在上、列表在下，中间隔一行说明）；列表数字旁边标"本工作台片子合计"；★ 绝不把两者并排在同一排 |
| R-拟 | **"算出来的"被当"看到的"** | 中 | 预估值一律显式标灰，绝不与实测值并排（沿用工程老规矩） |
| R-拟 | **多平台合计口径被误解**（"每平台各取最新一份"这条规则不直观） | 中 | 列表行上挂平台标签；点进作品页能看到"这个数是由哪几条快照加出来的" |
| R-拟 | **跨项目汇总慢**（要扫所有项目） | 低 | 只读 `review.json` 小文件；结果缓存 |
