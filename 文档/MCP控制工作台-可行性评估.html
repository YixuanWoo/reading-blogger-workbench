给工作台写一个 MCP · 可行性评估 目标：做测试（尤其 T-05 / T-17 这类 GUI 实点验证）时，AI 能代你点界面

结论：可行，没有技术禁区 —— 但「贵」的不是 MCP，是给工作台开一扇「遥控窗」。

MCP 那一层只是个小胶水（照抄现有 bridge.js 就行）。真正的活是：往工作台进程里装一个控制端口， 再把界面上一堆 private 的「点按钮」动作抽成能被外部调用的命令。工作量的大头在这里，不在 MCP。

ControlServer

↓  Dispatcher.Invoke（必须！）
工作台
在外壳上跑：GoTo / OpenProject / 反射调页面动作 / 读 WorkbenchState · 外壳已有 6 个公开入口，其余是 private 需补
已经有的 要新写的（就这两块 + 一点命令封装）

诚实说难点 按"卡人程度"排序，前两条才是真成本

动作语义化
★★★
页面上的动作全是 private void BtnXX_Click，而且都假定"已经选好了某一行、某个项目"。 要暴露成命令，得先理清前置条件和返回值。这是最大的活，也最容易"做一半"。
省事的办法：先做一个通用反射调用口（POST /invoke {类, 方法, 参数}），几乎零改造 —— 代价是调用方要自己知道方法名。
UI 线程调度
★★★
HTTP 回调在后台线程，碰任何控件都会抛"调用线程无法访问此对象"（这坑工作台已经踩过，crash.log 里有实锤）。 必须 Dispatcher.Invoke，且不能在后台线程同步等界面 —— 会死锁。
长任务两段式
★★
渲染、Agent 调用都是分钟级。MCP 工具不能傻等，得"发起 → 轮询状态"。 好消息：工作台的 /ping 已经是这个模式，直接抄。
后门风险
★★
控制端口会长在产品 exe 里，任何本机进程都能遥控工作台。 要做成默认关闭 + 只绑 127.0.0.1 + 可选口令，或者干脆 #if DEBUG 只在调试包里存在。
抢你的界面
★★
我操作的是你正开着的那个实例。我切页面会打断你。要约定"我操作时你先别动手"，或者允许我另起一个验证实例（但这会撞单实例锁）。
MCP 协议本身
★
定义工具、收发消息 —— 几百行的标准活，bridge.js 现成骨架，没有难点。
