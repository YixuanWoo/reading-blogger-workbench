## 一、潜在风险 / 问题（R）

### R-01 剪辑接缝的「咔哒」声 —— 要不要给精剪切点加 crossfade

- **状态**：⏸ 已决定**暂不做**（2026-10-01）。触发条件出现再说。
- **是什么**：crossfade（交叉淡化）= 接缝处让两段音频重叠几毫秒，一段淡出、一段淡入，
  波形在接缝处连续不断点，就不会有"咔哒"。
  硬切时波形会突然跳变，喇叭为了跟上这一下多出来的冲程，听起来就是一声轻响。

  两类接缝要分清，别混为一谈：

  | 类别 | 数量 | 谁造成的 | conform（T-07）管不管 |
  |---|---|---|---|
  | **A 类** 块接缝 | 51 处 | **组接**环节（旧的 `warp_to_blocks` 拉伸音频，每块边界时间不连续） | ✅ 管 —— 改成「音频零处理 + 画面 conform」后自动消失 |
  | **B 类** 精剪切点 | 184 处 | **精剪**环节（把源音频切成 184 段再拼，切点波形不连续） | ❌ 不管 —— conform 不碰音频，消不掉 |

- **什么情况下该管它**：**你在剪辑 / 听成片时，如果总听到"咔哒"、「啪」这类接缝杂音**。
  一条片子偶尔一声不用管；**反复出现、位置固定、能听出规律**，就说明 B 类接缝真的在响。
  （多数切点落在人声气口上，波形本来就接近 0，实际多半听不出来 —— 但别凭猜，用耳朵定。）
- **先怎么验（不用改任何东西）**：直接听
  `项目\<项目名>\stages\05-assemble\audio-final.wav`（原始音频版），或听已出的成片 `*-成片.mp4`。
  B 类的接缝在现有素材里本来就在，不需要等出片流程跑完。
- **真要做的时候怎么做**：对相邻两段的接缝各加 2~5ms 淡入淡出（ffmpeg `afade`），一次重编码。
  在 `FFmpegAssembler.BuildAudioGraph` 里给相邻片段之间插交叉段即可。
- **代价 / 为什么当时不做**：它**动了音频** —— 直接破掉「音频全程零处理」这条铁律，
  也破掉「成片音频可以与精剪源逐样本对账」的验收前提。所以要单独立项、单独验收，不能顺手做。
- **涉及**：`LiteCut.Core/Media/FFmpegAssembler.cs`（音频图）

### R-02 安全帧 3 帧不够用（动画收尾被裁）

- **状态**：⏸ 观察中。当前参数 = 3 帧（@30fps = 0.10s）。
- **是什么**：每镜画面 = 该镜时长 + 3 帧静止尾，⑤ 组接时把这 3 帧裁掉。
  这 3 帧是给"渲染取整误差 + 拼接对齐"留的缓冲，**动画的有效内容必须在音频结束前收住**。
- **什么情况下该管它**：成片里发现**某些镜头的动画（最后一句词、最后一个数字）还没收完就被切了**，
  或者画面在接缝前显得"戛然而止"。那说明 3 帧的缓冲不够，动画设计也压得太满。
- **真要做的时候怎么做**：把 `RenderSpec.SafetyFrames` 从 3 调到 4 或 5（**改一个数字**，链路早就通了），
  然后**按新规格重渲**受影响的项目。同时检查 `ShotPrompt` 里那条"内容须在时长内收住"有没有被 Agent 贯彻。
- **顺带**：调整后旧产物一律作废（见 R-05），要重渲才吃得上。
- **涉及**：`工作台/Workbench/RenderSpec.cs`、`Agent/ShotPrompt.cs`、`Agent/RenderPrompt.cs`

### R-03 conform 让画面从「无损直拷」变成「过一次编码」

- **状态**：⚠ 已知代价（T-07 引入）。目前判断可接受。
- **是什么**：旧的组接是 `-c:v copy` 一个字节都不重编码（几秒拼完、画质零损）。
  新 conform 要对每块做 `trim` / `tpad` 来对齐时长，**必须重编码**，因此：
  ① 出片慢很多（51 块 1080p30 全片过一次编码）；② 画面多一代 h264 损耗。
- **为什么仍然值得**：换来的是音频零处理（不变调、可逐样本对账）+ 音画严格对齐。
  设计上认定这个交换是划算的（旧方案的音频拉伸虽然保住了画质，但动了声音）。
- **什么情况下该管它**：出片后**肉眼觉得画质明显比渲染产物差**（糊、块状），
  或出片耗时到了不能忍的程度。
- **真要做的时候怎么做**：
  - 画质：把 crf 调小（18 → 14~16）或换更慢更好的 preset；有 NVENC 时优先用硬件编码器提速。
  - 或者换思路：走「中间无损格式」路线（先出 ProRes/FFV1 再编码），但磁盘占用大得多。
  - 极端情况可以考虑"只对需要裁的块重编码、其余直拷"，但实现复杂度高很多，非必要不做。
- **涉及**：`LiteCut.Core/Media/FFmpegAssembler.cs`

### R-04 每块末尾的帧对齐静音（≤1 帧）

- **状态**：⚠ 已知代价（T-07 引入）。目前判断无感。
- **是什么**：视频只能按整帧出片，音频段长度却是任意小数。为了音画严格对齐，
  每块音频末尾要补上 `(整帧化目标时长 − 音频段时长)` 的静音，**每块 ≤ 33ms（@30fps），平均约 17ms**。
  音频内容一个采样都没变，只是在末尾插了一小段静音。
- **为什么基本无感**：块边界就是**句末**（语义合并保证切点落句末），句末本来就有自然气口，
  十几毫秒的静音正好混在里面。
- **什么情况下该管它**：听成片时觉得**节奏发"顿"、字与字之间像被卡了一下**，
  且这种顿感有规律（每句话末尾都有）。
- **真要做的时候怎么做**：
  - 治本：让**分镜切块时把块边界对齐到整帧**（48kHz 一帧 = 1600 采样，是整数），
    这样音频段长度天然是整帧倍数，残差为 0，不需要补静音。代价是要动切块逻辑，且影响已有项目。
  - 或者接受"块内不足一帧的错位但不累积"的另一种 conform（时间重映射），但会引入画面顿挫，不推荐。
- **涉及**：`LiteCut.Core/Media/FFmpegAssembler.cs`、`LiteCut.Core/Engine/ShotSplitter.cs`

### R-05 旧规格渲染产物与新 conform 不兼容

- **状态**：✅ **已按"不强裁"实现（T-07 / V1.0.4）**。下次对老项目出片时留意即可。
- **是什么**：安全帧是 2026-10-01（V1.0.3）才加进规格的。
  **在此之前渲好的产物没有那 0.10s 静止尾**（实测 Δ 只有十几毫秒的整帧余量）。
  拿新 conform 去裁它们，**裁不到 3 帧那么多**，硬裁就会切进动画内容。
- **什么情况下该管它**：对**老项目**（如"思辨与立场"那 51 块）重新组接出片时。
- **实现口径（V1.0.4 落地，无需再改）**：目标时长**恒等于该块音频段长度向上取整到整帧**
  （`TargetSecOf`），**never 写死裁 3 帧**：
  `ConformOne` 的两遍 `trim=end_frame=F` 中间夹一个 `tpad=stop_mode=clone:stop_duration=T`，
  所以画面偏长就裁掉多余、偏短（老产物可能短）就冻最后一帧补齐，两边都不会出错，
  只是那一块少了安全余量。无头验证已覆盖"源块比目标短/长"两种情形。
- **想让安全帧真正生效**：只能**按新规格重渲**（重渲前 ④ 页会给逐块 Δ 预览）。
- **涉及**：`LiteCut.Core/Media/FFmpegAssembler.cs`、④ 渲染页

### R-07 `render-spec.json` 的 `OutputDir` 曾同时背两个含义（2026-10-01 已治本）

- **状态**：✅ 已修（V1.0.5 / T-10）。留档是为了记住这类坑。
- **是什么**：一个字段塞了两个概念：
  - 分镜页（`Step2ShotView.BuildSpec`）写的是 `stages\04-render` —— **渲染过程文件**目录；
  - 渲染页（`Step3RenderView`）写盘时写的是 `<项目夹>\渲染产物` —— **产物**目录。
  两页都会写同一份 `render-spec.json`，于是**谁最后保存就听谁的**。
- **会怎么伤到人**：`RenderTasksFile.ResolveOutputDir` 与渲染页 `Mp4Of` 都拿这个字段去找
  `shot_xxx.mp4`。一旦读到分镜页写的那份，就会去 `stages\04-render` 里翻产物 ——
  **51 块明明好好躺在 `渲染产物\`，界面却说"一块都没有"**。
  而且两处兜底都还是 `<引擎根>\renders\<名>`（"在引擎目录里给每个项目建子夹"的老口径），
  与项目自包含原则冲突。
- **怎么修的（治本，改约定而非改个例）**：
  - 约定收口到 `RenderSpec.RenderOutputDirOf(项目夹)` 一个静态方法，**全项目只此一处**；
  - `ProjectStore` 新增 `RenderOutputDir`，并与 `RenderStageDir` 写明分工（产物 vs 过程）；
  - 分镜页 / 渲染页 / 两处兜底全部改用它；`_stageDir` 不再从 `_spec.OutputDir` 反推。
- **教训（下次加"落盘字段"时照这条办）**：**一个字段只能有一个语义**。要让两个页面写同一份文件，
  就必须保证它们算出同一个值 —— 否则留痕文件会退化成"最后保存的人说了算"，
  而且**极难被发现**：两条路各自都跑得通，只有换个入口进来才露馅。
- **涉及**：`ProjectStore.cs`、`RenderSpec.cs`、`Views\Step2ShotView.xaml.cs`、
  `Views\Step3RenderView.xaml.cs`、`RenderTasksFile.cs`

### R-08 首次打开老项目时，基线回扫会把「陈旧产物」当成「已就绪」

- **状态**：⏸ 已知代价（2026-10-01，随 V1.1.0 / T-16 引入）。设计上接受了这个折中。
- **是什么**：产物清单 `render-manifest.json` 用**内容指纹**判「待重渲」。老项目第一次打开时清单还不存在，
  于是 `RenderManifest.BackfillMissing` 把**此刻磁盘上已有的每个产物**记成基线（指纹 = 当前镜头表算出来的那个）。
  好处是**不会一打开就 51 镜全标"待重渲"**（那才是更糟的假警报）。
  代价是：**如果那份产物在你上次改完镜头后一直没重渲**，它的基线会被记成"和现在的镜头表一致" → **不提示重渲**。
  （表现：界面说「已就绪」，实际画面还是老的。）
- **什么情况下该管它**：怀疑"某镜明明改过却显示已就绪"时。判断口诀 ——
  **基线只反映"打开清单那一刻磁盘上有什么"，不反映"它是不是最新的"**。
- **真要做的时候怎么做**：给基线加一个**可信度标记**（`baseline: true`），
  凡是基线条目**一律显示成「未校验（基线）」而不是「已就绪」**，由用户点一下才升级成"已就绪"。
  或者：把基线时间与 `shotlist.json` 的 `CommittedAt` 对比，产物早于交接时间 → 直接标「待重渲」。
- **涉及**：`工作台/Workbench/RenderManifest.cs`（`BackfillMissing`）、`Views\Step3RenderView.xaml.cs`（`Manifest` 属性）

### R-09 迁移中途「进程被杀」会留下孤儿 `.reindex-*.tmp`，无启动自愈

- **状态**：⏸ 已知代价（2026-10-01，随 V1.1.0 / T-16 引入）。概率低但后果重。
- **是什么**：搬迁用**双缓冲**（先全部 `→ *.reindex-<token>.tmp`，再全部 `→ 正式名`）。
  **异常**会被 `catch` 住并自动 `Rollback`；但如果是**进程被强杀 / 断电**（不是抛异常），
  就可能停在"第一遍做完、第二遍没做"的中间态 —— 磁盘上全是 `shot_00X.mp4.reindex-xxxx.tmp`，
  看着像"产物全没了"，且**下次启动不会自动认领这些 tmp**。
- **什么情况下该管它**：交接（点「应用到下游」）时被打断、或看到一堆 `.reindex-*.tmp`。
- **真要做的时候怎么做**：① 启动时扫白名单目录里的 `*.reindex-*.tmp`，
  若能匹配回模板名就自动续跑第二遍（或提示"上次搬迁没做完，是否继续 / 复原"）；
  ② 或把 `ReindexLog` 落盘时机提前到**动手之前**（现在失败才写），崩溃后凭日志自愈。
- **涉及**：`工作台/Workbench/ReindexMigration.cs`（`Execute` / `LoadLog` / `LogPathOf`）

### R-10 桥接凭据文件会过期 → 又退回「点了没反应」（2026-10-01 T-04 实机验证暴露）

- **现象**：`POST /wake` 报 `connect ECONNREFUSED 127.0.0.1:51078`（旧端口）；工作台走降级文案。
- **成因**：`%LOCALAPPDATA%\workbuddy\.gateway_creds.json` 记的是**上一个会话**的网关端口/密码
  （该文件**只读、由宿主写、不保证刷新**），而**网关端口与密码每个会话都变**
  （实测：端口 `64563` → `59769`；密码长度同为 43 但**值不同** → **不能靠"扫描端口自动发现网关"**）。
- **现有缓解（14:40 加固后）**：凭据优先级 = `会话 env` > **`%LOCALAPPDATA%\LiteCut\bridge-creds.json`（实时凭据）** > 官方文件。
  实时凭据文件由**当前 Agent 会话写入**，桥接**每次请求都重读** → **工作台自启的桥接（无 env）也能拿到新鲜凭据**
  （已实测：清空 env 启动 → `/health` 的 `credsSource` = `live`，`gatewayPort` 正确）。
- **仍开着**：实时凭据文件**仍需有人写**（目前是 Agent 会话写）。宿主重启后端口一变，旧值即失效。
  候选长期解：**SessionStart hook** 让会话自动刷（待用户拍板）。
- **附带行为**：消息投进会话后要过 `waitForSessionIdle` —— **会话正忙时是"排队"，不是立即执行**（不会丢，但也别指望秒到）。
- **涉及**：`工具\agent-bridge\bridge.js`、`工作台\Workbench\Agent\AgentBridge.cs`

### R-12 桥接进程的存活取决于"谁拉起它"（2026-10-01 二次复验暴露）

- **现象**：第一次点按钮成功（界面显示"已通过桥接自动唤醒"），**再点变成 `ECONNREFUSED`（连接被积极拒绝）**
  —— 桥接进程在这两次之间**死了**。
- **成因**：桥接若是**由 Agent 会话侧**拉起，它就在宿主进程树里；**宿主重启会把整个进程树带走**
  （旁证：宿主 14:36 重启时，两个 MCP 的 node 进程启动时间同步刷新为 `14:36:5x`）。
  另外桥接此前**没有任何全局异常保护**，一次未捕获异常即可静默退出。
- **处置（14:40 已做）**：① 加 `uncaughtException`/`unhandledRejection` 保护（不退进程）；
  ② 日志落 `bridge.log`，**每次 `/wake` 都留痕**，可分清"工作台没打过来"还是"转发失败"；

  → **一次 ffmpeg 都没启动过**。26 块产物本身齐全。）
- **根因**：`FinalScriptBuilder.FromTranscript` **以句为纲**，每行 `StartSec/EndSec`
  = 「该句覆盖的第一个块的时间轴起点 → 最后一个块的时间轴终点」。
  于是**行是"点状"的** —— 一句话有归属，**句子与句子之间那口气不属于任何一行**。
  而 `ShotSplitter` 三种切法一律取「块尾 = 末行.EndSec」
  → 落在**块边界**上的留白**整段丢失**。
  - 精确分解：**片头前导 0.560 + 落在镜头边界上的句间留白 0.780 = 1.340**。
    全片句间留白 7.034s / 54 处；落在块**内部**的 6.254s 被块长盖住（无碍）。
  - ★ **精剪没有被忽略**：删减、挪块都生效（决策轴 = `DecisionTimeline()` ← `KeepRanges()`，精剪优先）。
    漏的只有"留白的归属"这一件事。
- **为什么后果比"少 1.3 秒"严重**：组接是「从连续音轨上按每块的时长窗口切一段贴上去」
  （`BuildAudioGraph`，film 轴 = 各块首尾相接）。两轴不同长 → **每块分到的音频整体挪位**：
  片头错 0.56s、往片尾累积到 1.34s → 音画错位 + 末句被切掉半截。**自检拦得对，只是没说清。**
- **修法（V1.10.13）**：`ShotSplitter.Split()` 返回前加 `FillToTimeline(spans, script.TotalSec)`：
  首块 `StartSec = 0`、`spans[i].EndSec = spans[i+1].StartSec`、末块 `EndSec = totalSec`。
  口径 = **气口归前一块**（一句话说完，画面多停一会儿）。
  - **数学保证**：Σ块长 ≡ 决策轴总长（望远镜求和，**与怎么切无关**）。
    实数据离线复算 **187.512 → 188.852，误差 +0.000000**。
  - ★ **只动时间窗，一个字不动 `SourceStartSec/SourceEndSec`** ——
    镜头 ID 靠源区间继承（`Step2ShotView` 的 `byRange`），所以重切后 **ID 不丢**、只标「待重渲」。
- **★ 推翻一条旧认知**：出片被拦时的提示「去第③步重算口播稿并重切镜头」——
  **V1.10.13 之前点了也没用**（重切走同一套算法，切完照样少 1.34s）。
  提示语本身没说错（"分镜确实不是按当前决策切的"），错的是"重切能救"这个**隐含承诺**。
- **★ 这个缺陷一直存在**：以前的片子同样在边界上丢气口，只是差值在 0.5s 阈值以内没被拦。
  用户这次精剪留的气口多（1.34s），才把它顶到明面上。
- **代价（离线复算本项目，25 个语音镜头）**：**20 个时长会变（要重渲）**，
  3 个完全不变（`#6 s04` / `#11 s09` / `#16 s15`）；单块幅度 **-1.38 ~ +1.38s**。
- **★ 用户拍板 B 方案（同日）**：「已经渲染出来了，重新渲染费时间费 token 没啥意义」
  → **V1.10.14 组接侧落地**（见更新日志）：`Step4ExportView.ComputeBlockLens()` 按决策轴映射重算每块目标窗口，
  **Σ 目标 ≡ 决策轴总长**（实测 198.852 = 198.852，音画差 +0.000）；插片插点同步换轴。
  本期成片已用一次性 CLI（引用 LiteCut.Core）直接产出：**199.200s / 26 块 / nvenc 7.9s**，
  7 块尾部定格补帧（最长 0.718s，定格的是该块自己的收尾帧，视觉连续）。

### R-23 ★ 起外部脚本**必须显式设工作目录 + 掐掉 `pause`** —— 否则留僵尸把文件夹钉死（2026-10-15 搬家收尾暴露，**✅ 已修 V1.13.2**）

- **状态**：✅ 已修（`ArchiveService.TryUpdateLedger()` 加 `WorkingDirectory` + 命令行带 `< nul`）。
  ★ 但这条**不止管台账那一个脚本** —— 凡"从工作台起外部 .bat/.cmd"的地方都要照这个规矩。
- **症状**：`D:\视频创作\工作台` 送回收站**恒失败（返回码 32 = 文件被占用）**，
  但目录里**逐文件**改名探针全过、`mkdir/rmdir` 也正常 —— 即"**目录本身**被一个看不见的句柄抓着"。
  上一轮排查手段用尽（openfiles 没开、句柄枚举受限于沙箱），只能记成"重启后再说"。
- **怎么揪出来的**（这套手法留着复用）：
  1. 对照实验：在**同一父目录**下新建测试目录送回收站 —— 成功 → 排除"回收站/环境"问题；
  2. 重启管理器 `RmGetList` —— 要管理员，被拒（`rc=5`）；
  3. ★ **读 PEB 拿每个进程的"当前工作目录"**（`NtQueryInformationProcess` → PEB+0x20 → `ProcessParameters+0x38` → `CURDIR.DosPath`）——
     同用户非保护进程都能读，**不需要管理员**，一击命中：
     `cmd.exe`（PID 19544）= `cmd.exe /c "…2-增量更新.bat"`，**15:31:15 启动、19:53 仍存活**，
     工作目录正是那个删不掉的旧文件夹。`taskkill /F` 一执行 → 旧目录**立刻删掉**。
- **根因**（两个原因凑一块才成灾）：

| # | 原因 | 单独看 | 凑一起 |
|---|---|---|---|
| ① | `ProcessStartInfo` **没设 `WorkingDirectory`** → 子进程**继承工作台自己的当前目录** | 子进程跑完就退，没事 | 子进程只要不退出，就**永久**抓着那个目录（Windows 上"当前目录"是**不允许删除/改名**的句柄） |
| ② | bat 末尾 `pause`，而它是**最小化后台**起的、永远没人按键 | 手动双击时正好用于"看完结果再关窗" | `cmd.exe` 永不退出 → ① 变成永久，**归档一次埋一颗雷** |

- **教训**：搬完家后工作台自己在 `D:\工作台`，不修的话**下一颗雷就埋在新家上**。
  ★ 附带认知：**"隐形句柄"未必隐形** —— 先想"谁的当前目录在这儿"，
  再想"谁打开了这个文件"；**目录**的占用者绝大多数是 CWD，不是文件句柄。
- **✅ 对照实验复现（受控证据）**：两个"末尾带 `pause`"的脚本，都用 ShellExecute（新开控制台）起 ——
  **老写法**（不设工作目录、无 `< nul`）：2 分半后**仍存活**，其所在目录**改名报 32**；
  **新写法**（设工作目录 + `< nul>`）：**已自行退出**。杀掉前者 → 那道锁**立刻消失**。
  ★ **方法教训**：用 `subprocess`（直接继承 stdin）**复刻不出**挂起 —— 会拿到 EOF 假象；
  必须走 ShellExecute **新开控制台**才复刻得出来。
- **验证**：另单独验证 `< nul>` 语法（ShellExecute 起带 `< nul>` 的命令，脚本确实跑完并正确写盘）。

**★ 2026-10-12 补充侦察：能不能把「连接功能」写进工作台？（用户提问 · 只调研、未实施）**

- **先纠一个常见误解：WO Mic 不是开源的。** 官方客户端（`WOMicClient.exe`）与驱动是**闭源免费**软件，
  手机端 App 同样闭源（Play 版带广告/内购）。网上能搜到"WO Mic 是开源项目"的说法**是错的**
  （有的是内容农场把占位链接直接写成了 GitHub 地址）。社区确有两份**非官方**成果：
  ① 20kdc 的**协议笔记 + Rust 版 Linux 客户端**（GitLab，黑盒 Wireshark 逆向，约 2 年前）；
  ② RokasKil 的 WinAPI 客户端（**不含驱动**，要另配第三方虚拟声卡）。它们是**第三方逆向件**，不等于官方开源。
- **★ 关键发现（本机实测）：连接参数全在注册表里。** 客户端把配置存在
  **`HKCU\Software\Wolicheng\WOMic`**（exe 里能直接读到 `Software\Wolicheng\WOMic` 字符串 +
  `RegOpenKeyExW` / `RegSetValueExW` 调用）。已有键：`wifiAddr`（WiFi 连的地址）、`hotSpot`（配件热点/直连地址）、
  `bluetoothDevice`（蓝牙 MAC）、`transport`（连接方式枚举：Bluetooth / USB / Wi-Fi / Wi-Fi Direct 四种）、
  `controlPort`、`mediaPort`、`autoConnect`（空=关）、`bufferSize`、`language`、`Install_Dir`。
  → **这意味着"写进工作台"可以完全不用碰协议。**

| 路线 | 做法 | 成本 | 主要代价 |
|---|---|---|---|
| **甲** | 工作台**写注册表**（`wifiAddr` / `transport` / `autoConnect`）→ **拉起** `WOMicClient.exe` → 它自动连上 | **最低**（几次改动级） | 依赖它的版本与注册表键名（它一升级就断）；工作台**拿不到"连上没连上"的状态**；界面上会多一个外部程序窗口 |
| **乙** | 工作台**自己实现客户端**（按逆向协议收发 Opus 包） | **最高** | 私有协议可能被官方改；逆向笔记是 2 年前的黑盒结论、其作者自述"丢包恢复行为没有实现"；**驱动仍是人家的**，绕一圈还是要靠它的虚拟声卡 |
| **丙 ★推荐** | **绕开虚拟声卡**：录音台直接收手机音频并落盘 | 中等 | 要选定（或自建）一个手机端音频源 |

- **为什么推荐丙**：**录音台要的是"音频文件"，不是"系统里多一个麦克风"。** 虚拟声卡这一层是为
  "让别的软件也能当麦克风用"而存在的；工作台自己要用，根本不需要这个中转。
  ★ **现成方案：`scrcpy`（全开源 Apache-2.0）** —— `scrcpy --audio-source=mic-unprocessed --no-video --record=xxx.opus`
  （或加 `--audio-codec=raw` 直接拿未压缩 PCM），手机麦克风信号**沿 USB 线直接落到电脑文件**，
  **零驱动、零虚拟声卡、零第三方手机 App**。
  ★ **额外好处**：`mic-unprocessed` 取的是**未经手机降噪/AEC 处理的原始信号**，
  正好避开"手机自带音频处理因机型而异、音色不可控"这个坑；`--audio-source` 另有
  `mic` / `mic-camcorder` / `mic-voice-communication` 等档位可横向对比选型。
  ★ 次选：自写一个手机端小 App（AudioRecord + Opus + UDP），工作台侧收——全自主，但多一份手机端开发量。
- **什么时候做**：真要开「录音台」时。**建议第一步就是半小时的"输入源实测选型"** ——
  同一段话让手机分别走 **WO Mic** 与 **scrcpy** 各录 10 秒，比延迟和音色，再决定走哪条路线。
- **涉及**：走**路线甲** → 注册表读写 + 拉起外部进程（**不碰** `LiteCut.Core` 主流程）；
  走**路线丙** → 一个"外部录音进程"的启停与落盘（scrcpy 无源码可改，只当子进程用）。**当前一行代码都不动。**

**★ 2026-10-12 实测补充：这个虚拟麦克风「不是常驻设备」（本机排障得出，对录音台设计很关键）**

- **现象**：用户在「声音设置」里**看见过**「麦克风 (WO Mic Device)」，过一会儿**又没了**。
- **查出的事实**：驱动服务 `WOVAD` 在跑、`ROOT\MEDIA\0000`（WO Mic Device）状态 OK、
  客户端进程活着且**与手机 TCP 已连接**（`192.168.110.79:8125`）、系统防火墙三档全关且安装器已加放行规则
  —— **一切正常**。而音频端点 `{dca43569-…}` 在 `MMDevices\Audio\Capture` 里的 `DeviceState` 低 4 位 = **1（ACTIVE，正在用）**。
- **结论（重要特性）**：**它是"跟着连接走"的虚拟设备** —— 客户端**连上手机之后才把它挂到系统上**，
  **连接一断，客户端就把它从系统里摘掉**（端点随即消失），重连成功才回来。
  实锤：同一次会话里客户端与手机的 **TCP 本地端口 15:33 是 55285、15:35 变成 58668** → 中途断过一次又重连。
  → 用户"看见又没了"只是**正好撞上断开的那一段**。**不是装坏了。**
- **★ 对录音台的含义**：必须把「输入设备」当成**会随时消失的东西**来对待
  （**连接状态 = 音频源可用性**），不能像本地麦克风那样"开局选一次就完事"。
  反过来也是好消息：**"设备在不在"本身就是一个可靠的"连上了没"信号**——路线甲里"拿不到连接状态"那个缺点，
  可以靠监听这个设备来补。
- **官方自检口**：客户端 **Help → Statistics** 看 **`Driver state`**（`1` = 驱动正常；`0` = 驱动没工作）。
  抓日志：**Options → Advanced → 勾 Enable debug mode** → 退出重开 → 复现 → 退出，
  日志落在 **「文档」文件夹** `womic_debug_*.log`（注意：不是 TEMP、不是安装目录）。
- **断线常见原因（官方 FAQ）**：① 手机 App 要在**前台 + 屏幕常亮**（安卓只给前台高优先级）；
  ② **蓝牙与 WiFi 同占 2.4G，会互相干扰** → 用哪个关哪个；③ 官方建议**优先用 USB 线**（更稳、延迟更低）；
  ④ 电脑熄屏/无线网卡省电会让它**每 5 分钟断一次**（电源选项里关掉无线网卡省电）；
  ⑤ media port 从 60000 改成别的（如 12345），避开占用与拦截。

**★★ 2026-10-12 第三次排查：「能看见设备」不等于「有声音」——两条判据级教训**

- **现象**：设备重新出现在列表里，用户点「测试麦克风」**完全没声音**；iPhone 上的麦克风标记也没出现（后来才出现）。
- **实测（本机，全部是硬数据）**：
  1. **dshow 枚举确实能看到它** —— `ffmpeg -list_devices` 列出 `"麦克风 (WO Mic Device)" (audio)`
     （`@device_cm_…\wave_{DCA43569-52B0-4140-ADD1-B63D2871F72C}`）→ **设备层没问题**。
  2. **但录出来是"数字静音"**：用 ffmpeg 从该设备录 8 秒 → `mean_volume: -91.0 dB` / `max_volume: -90.3 dB`
     （16bit 音频的下限就是 -91dB；250 KB 的文件里**一个字节的有效声音都没有**）。
  3. **客户端一个字节都没收到**：`Win32_Process.ReadTransferCount` 采样**10 秒增量 = 0 字节**
     （更早一次还有 2 KB/6s 的心跳 → 后来连心跳都没了）。**录音期间（端点被真正打开）依然是 0。**
  4. **TCP 却仍显示 `Established`**（本地 58668 → 192.168.110.79:8125）= **僵尸连接（half-open）**，
     客户端自己不知道手机侧早就不发了。
  5. 网卡只有 WLAN 一块有效（192.168.110.138，与手机同在 192.168.110.0/24；其余网卡都是 169.254 无效地址）
     → **排除"多网段/发错地址"**；UDP 60000 绑定正常；安全软件只有 Windows Defender（且防火墙三档全关）。
- **★ 教训 1（判据级）**：**"设备能枚举出来" ≠ "有声音"。**
  dshow / 声音设置里看得见它，只说明**驱动把端点挂上了**，不代表**数据在流**。
  **判定"到底有没有声音"的唯一硬指标 = 真的录一段 + `volumedetect`**（`-91dB` = 静音，铁证）。
  与 R-17 / R-19 的**判据铁律**同源：**看磁盘 / 信号事实，不看"名义状态"。**
- **★ 教训 2（判据级）**：**TCP `Established` ≠ 连接可用。**
  Wi-Fi 断链时电脑端会留下"僵尸半开连接"，客户端读数停在 0 也不报警。
  → **比 socket 状态可靠得多的健康指标 = 客户端进程的 `ReadTransferCount` 增量**（持续 0 = 已死）。
  将来录音台要做"连接健康度"，就按这个采样，别信 socket 状态。
- **★ 教训 3（工具坑，避免重踩）**：读 `HKCU\…\Wolicheng\WOMic` 的 `wifiAddr` **要用 `reg query`**。
  用 PowerShell `Get-ItemProperty` + 遍历 `PSObject.Properties` 会**串到内存垃圾**，显示出
  `192.168.110.79䄊▭緹…` 这种乱码假象（本次据此一度误判"配置被写脏"，虚惊一场；
  真实值 `wifiAddr REG_SZ = 192.168.110.79`）。
- **★ 教训 4（选型，重要）**：**iPhone 只能走 Wi-Fi。**
  iOS **不支持** WO Mic 的 USB / 蓝牙模式（官方 iOS 版只有 Wi-Fi 一条路），而 Wi-Fi 恰是最不稳的那条
  → **iPhone + WO Mic 的可靠性要打问号**。且上一条推荐的 **`scrcpy` 是 Android 专有**（不支持 iOS）
  → 若坚持用 iPhone，路线丙需要另找 iOS 端采集方案（可能无解，得回到"买麦"）。
  **录音台选型第一步必须先确定手机阵营**（Android 有 scrcpy 这条全开源硬路；iPhone 目前只有 WO Mic 这条软路）。
- **现场修法**：**断开重连**（客户端 Disconnect → Connect；或退出客户端重开再 Connect，IP 已存注册表会自动带出）。
  连接恢复正常后，端点会重新挂上、`ReadTransferCount` 增量会变正、录音才有声音。
- 本次**依然是只诊断、未改任何代码**；8 秒静音样本留档 `D:\系统工具\_diag\womic_test.wav` 作证据。

- **★★★ 判据级修正（**推翻**第四次的说法，本轮最重要的一条）**：
  **`ReadTransferCount` 对 WO Mic 这类 UDP 流不可靠** —— 客户端收音频走的是**套接字通道**，
  **不计入该进程的 I/O 计数器**，于是出现"**明明在收、读数却是 0**"的假象，直接误导了第三、四两轮判断
  （包括"打开录音端点数据流反而归零"那条，**纯属计数假象，不是真故障**）。

  ① `netstat -s -p udp` 取「**接收的数据报**」增量（**>10 个/秒**即音频在流）；
  ② **实际录音 + `ffmpeg -af volumedetect`**（`-91 dB` = 数字静音；**`> -60 dB` = 有信号**）。
- **遗留（不算故障，转给录音台设计）**：音量偏小（说话 `mean -32 dB`），
  将来录音台要留**输入增益 / 先试录 10 秒**的口子。
- 本次**仍然一行业务代码未改**（纯环境排障）。

**★ 2026-10-12 追加：宿主软件（达芬奇等）看不到该设备怎么办**

- **现象**：链路已通（录音有声音、UDP 包在流），但**达芬奇（DaVinci Resolve）的音频输入设备列表里找不到 WO Mic**。

  **只在启动那一刻枚举一次音频设备**，之后不会自动刷新。
  实测：达芬奇进程 `14:55:52` 启动，而 WO Mic 客户端在 `15:24` 之后多次重启、端点是重新挂上的
  → 达芬奇手里的设备表**早已过期**。
- **解法**：**完全退出宿主软件 → 重新打开** → `偏好设置 → System → Audio I/O` →
  `Input device` 选 `Microphone (WO Mic Device)`（Windows 上走 **WASAPI**；若引擎被设成 ASIO 则看不到该设备）。
- **★ 对录音台的含义（硬顺序）**：**必须先连上手机、再启动宿主软件** —— 反了就看不到设备。
  这条以后要写进录音台的使用说明与"先试录 10 秒"的自检流程。
