## 0. 一句话结论

> ★★ **你说得对：这是整个工作流最不合理的一个缺口。**
> 「立项 → 撰稿 → 录音 → 成片 → 发布」全在公司里跑通了，
> **唯独最后一环「效果到底怎么样」断了**——出了片就没下文了。
>
> **所以本页不是「加个功能」，是把一条已经缺口的闭环补上。**

**三个决定（都基于「手动填也行」这个前提）：**

| 决定 | 内容 | 为什么 |
|---|---|---|
| ★ **不碰平台接口** | 第一版纯手动录入，一个字段都不自动抓 | 抖音创作者后台无公开 API；网页抓取要登录态、随时被改版打断。**这是最容易被"看起来很智能"骗进去的坑** |
| ★ **数据落项目里，不落飞书** | `<项目>\stages\06-review\` | 项目是**自包含**的铁律所在。复盘数据跟着片子走，才谈得上"经验沉淀" |
| ★ **画图用 WPF 原生，不引依赖** | `Canvas` 手绘 + 一套共用坐标换算 | 工程现在只有 NAudio 一个依赖。引图表库 = 引入维护与体积代价，**为 3 个图不值** |

## 1. 为什么这一环最该做（不是"锦上添花"）

### 1.1 你的规范里已经写死了闭环，但工作台里没有

`内容创作工作流` v1.6.0 明确写了：

```
「发布了」+ 发布时间 → 记发布日期；计算 7 天后日期写入「复盘日期」；
                      创建 at 定时任务；状态=已发布
（定时任务到点）    → 抓取播放/涨粉/点赞/收藏数据，写复盘报告存云盘，
                      更新项目数据与复盘结论，结论回填素材索引，状态=复盘完成
```

★ **这条规范是完整的、一直没变的。** 问题在于它 100% 落在**对话 + 飞书**上，
而"出片"这件事已经搬进工作台了。**搬家搬了一半。**

### 1.2 断链的四个点（已核实，不是推测）

| 环节 | 规范里有 | 工作台里 |
|---|---|---|
| ⑥ 发布 | 「写了」触发词 | ❌ **发布页已砍掉**（`NavTree.cs:16` 注释原文） |
| ⑦ 复盘 | 「定时任务到点」 | ❌ **从未存在过** |
| 数据中枢 | 飞书多维表格「视频作品与数据」 | ❌ 工作台**零处引用**飞书 |
| 飞轮 | 「复盘结论回填素材索引」 | ❌ 结论无处可查 |

★ 唯一留下的复盘相关产物是
`《思辨与立场》\export\抖音发布文案.md`（5087 B）——
**但它是发布"前"的物料**（标题三选一、正文、标签、封面建议）。发布之后呢？没有落点。

### 1.3 ★ 缺这一环的代价，是复利流失

> 你在规范里写了"复盘结论回填素材索引形成飞轮"。
> **飞轮的第一推动力缺失，后面全转不起来。**

具体损失三样：

| 损失 | 现状 |
|---|---|
| **不知道什么选题行** | 只有感觉。做过 3 支片，哪支数据好、为什么好，**记不住也查不到** |
| **不知道什么封面行** | `抖音发布文案.md` 里都写了封面建议（首推/抓眼球/收尾三选一），**但没人记哪张真点了** |
| **同一支片的多版本没法比** | 三选一的标题/封面是天然 A/B 结构，**录下来才能比，录不下来就永远是"我觉得"** |

★ **第三点是最可惜的**：你已经在做多版本了（三标题三封面），
但**结果数据没地方放**，等于把一个天然的实验白白扔掉。

## 2. 做成什么样：一个新页「复盘」

### 2.1 位置与形态

```
Global（没打开项目时）          InProject（打开项目后）
  灵感                →           0 写作台
  进行中                        1~5 音频粗剪…组接导出
  已归档                →      ★ 6 复盘      ← 新增
                                素材库
```

★ **放项目内（6），不放全局。**
理由：复盘数据是**某一支片**的属性（播放量、涨粉、结论），
跟片子长在一起才对。**跨片的对比是第二期的功能**（见 §5）。

### 2.2 页面三段（从上到下）

```
┌─ ① 数据录入 ──────────────────────────────────┐
│  平台 ▾ 抖音 │ 发布日 │ 统计日 │ 天数 7        │
│  播放 ____  完播率 ____%  点赞 ____  涨粉 ____ │
│  收藏 ____  评论 ____  转发 ____  主页访问 ____│
│  ── 自动算 ─────────────────────────────      │
│  互动总数  完播率  每千播放涨粉                 │
│  [保存]  [复制上次数据]                        │
├─ ② 图表 ─────────────────────────────────────┤
│  趋势：播放/互动 折线（跨项目时）               │
│  单片：完播率、互动构成 横向条                 │
│  多版本：标题/封面 A B 对比 柱状               │
├─ ③ 复盘结论 ──────────────────────────────────┤
│  三段式：这条讲对了什么 / 哪里没接住 / 下次改什么│
│  [生成报告] → stages\06-review\复盘报告.md      │
└────────────────────────────────────────────────┘
```

### 2.3 ★ 三个设计判断

**① 录入是"表格式"，不是一个表单框**
> 一屏能填完所有字段。理由：你每次复盘要填的字段**完全一样**，
> 做成逐行输入框会让你每次都"找哪个框是点赞"。

**② 图表只画三类，不做通用图表引擎**
> 趋势线 / 横向条 / 对比柱 —— **这三个覆盖 90% 的复盘需求**。
> 不做"用户自选图表类型"，那是 Excel 的活。

**③ 结论区是必填的，不是可填的**
> ★ 允许"这天还没到7 天" → 数据区可填，结论区显示"待复盘（还剩 3 天）"；
> **但一旦标记"已复盘"，结论不能为空**。
> 没有结论的复盘等于没复盘——这个约束要在保存时挡住。

## 3. 数据落点（项目自包含铁律）

```
<项目>\
  stages\
    06-review\                    ← ★ 新增，与 00-script / 03-shot / 04-render 同级
      metrics.json                ← 结构化数据（程序读）
      复盘报告.md                  ← 人读报告（你写/AI 生成）
```

★ **为什么落项目里，不落飞书**（这一条要跟你原来那版规范说清楚）：

| | 落项目 | 落飞书 |
|---|---|---|
| 跟着片子走 | ✅ 片子在 `项目\<名>\`，数据也在 | ❌ 片子在 D 盘、数据在云端，**两处** |
| 备份 | ✅ 随项目备份走 | ❌ 飞书挂了就没了 |
| 离线可看 | ✅ 打开工作台就有 | ❌ 断网就没了 |
| 跨片统计 | ❌ 要扫全部项目 | ✅ 天生在一张表里 |

★ **决定：项目内为主，飞书为可选镜像。**
理由：**工作台的铁律是"项目自包含"**（软件运行不依赖任何外部固定位置）。
数据跟着片子走，备份、迁移、离线全都免费。**跨片统计也不难**——扫 `项目\*\stages\06-review\metrics.json` 就行。

⚠️ **一条要提前说清的边界**：`metrics.json` 存的是**你录进来的数**，
不是从平台抓的。所以**它是唯一真相**，飞书那边的表格是给人看/给协作用的副本。
**不要**反过来以飞书为主——那样工作台就变成"必须联网才能用"的东西了。

### 3.1 数据模型（拟）

```csharp
/// <summary>复盘数据。★ 手动录入，不自动抓取（原因见 §0）。</summary>
public sealed class ReviewMetrics {
    public string Platform { get; set; } = "";      // 抖音 / B站 / 小红书…
    public string PublishedOn { get; set; } = "";   // YYYY-MM-DD
    public string MeasuredOn { get; set; } = "";     // 统计日（通常是发布 +7 天）
    public int    DaysOut     { get; set; }          // 发布到统计，几天

    // —— 核心指标 ——
    public long   Views      { get; set; }           // 播放
    public double CompletionRate { get; set; }       // 完播率 %（有些平台不给，手填）
    public long   Likes      { get; set; }
    public long   Comments   { get; set; }
    public long   Shares     { get; set; }
    public long   Saves      { get; set; }           // 收藏
    public long   Followers  { get; set; }           // 涨粉（这条最值钱）

    // —— 多版本对比（★ 复用你已有的三选一）——
    public string TitleVariant  { get; set; } = "";  // 实际发出去的那个标题
    public string CoverVariant  { get; set; } = "";  // 实际发出去的那张封面
    public double CoverClickRate{ get; set; }        // 封面点击率（抖音后台有）

    // —— 复盘结论（三段式）——
    public string Worked     { get; set; } = "";     // 这条讲对了什么
    public string Failed     { get; set; } = "";     // 哪里没接住
    public string NextChange { get; set; } = "";     // 下次具体改什么
    public string ReviewedOn { get; set; } = "";     // 复盘完成日
}
```

★ **落盘要点**：
- 写盘走 `ContractJson.Utf8NoBom`（R-13：BOM 会让外部解析器报错）
- 挂到 `ProjectModel` 的新段 `ReviewPart`（**加字段 = 安全**，老档案读到空对象）
- **不塞进 `OutputPart`** —— 那是渲染产物目录，语义不同

## 4. 分期与代价

| 期 | 做什么 | 规模 | 依赖 |
|---|---|---|---|
| **R1 · 录入 + 落盘 + 报告** | 复盘页骨架 + `metrics.json` + 三段式结论 + 导出 `复盘报告.md` | **~600 行 / 1.5 天** | 零 |
| **R2 · 图表** | `Canvas` 手绘三类图（趋势/单片/多版本对比） | **~450 行 / 1 天** | R1 |
| **R3 · 跨片总览** | 全局页看所有项目的复盘排行、趋势汇总 | ~400 行 / 1 天 | R1 |
| R4 · 飞书镜像（可选） | 把 `metrics.json` 推一份到飞书表 | ~200 行 | 需飞书凭据 |
| R5 · 半自动抓数 | 剪贴板导入后台数据 | ~200 行 | 平台格式 |

★ **建议只做 R1 + R2**。理由：
- R1+R2 就完整回答了"我这部片行不行"，**且不依赖任何外部系统**。
- R3 等你攒够 5~8 支片再做（和上次那份调研同一个道理：样本不够时排行是噪声）。
- R4/R5 都不解决根本问题，**优先级最低**——"看不到"的问题要靠"能录入"解决，
  不是靠"自动抓"。**别在 R1 之前碰它们。**

### 4.1 画图怎么实现（避免引依赖）

```csharp
/// <summary>★ 极简图表绘制。三类图共用这套坐标换算，不引任何图表库。</summary>
public static class MiniChart {
    // 折线：趋势。points = 至少2 个
    public static void DrawLine(Canvas c, IReadOnlyList<(string label, double val)> pts);
    // 横向条：单片指标对比。★ 中国人读条形图最顺，横着的条最容易比长短
    public static void DrawBars(Canvas c, IReadOnlyList<(string label, double val)> rows);
    // 柱状：多版本 A/B
    public static void DrawColumns(Canvas c, IReadOnlyList<(string label, double val)> cols);
}
```

★ **三条实现纪律**（照做，别学网上那些花哨图表库）：
1. **深色底**（工程已是深色主题），文字用**米白 / 亮金 / 浅蓝**，不用白底
2. **每根条/每个点都直接标数字** —— 不让人回头去对照坐标轴
3. 宽度用 `ActualWidth` 自适应，**不写死像素**（工程已有 812 vs 1096 的教训，V1.10.1）

⚠️ **"中国人读横条图最顺"这条是有原因的**：中文文字竖排阅读习惯让横向对比更快，
且指标名（"完播率""涨粉"）是长词，**竖着写要旋转文字**——工程约定**禁止旋转文字**。

## 5. 不做 / 留给以后（提前说清，免得反复问）

| 想要 | 判断 |
|---|---|
| **自动抓平台数据** | ★ **第一版不做**。抖音创作者后台无公开 API；网页抓取依赖登录态 + 会被改版打断。**手动填是正解，不是妥协** |
| **A/B 标题自动轮换发布** | 平台侧的事，且手动发一次就够 |
| **跨片排行榜** | 留 R3。样本 <5 支片时排行是噪声 |
| **AI 自动写复盘结论** | 值得做，但要**在你手写之后**（AI 读你的结论 + 数据，给建议），不能代替你写 |
| **完播率自动算** | ★ **做不到**。完播率是平台内部指标，工作台只能读成片时长去**估算**，不能当真值用。UI 上必须和真实抓取值**视觉分开**（这是写作台已有的规矩：`EstSec` 预估值标灰） |

★ **最后一条是硬边界**：任何"预估值"都不许伪装成"实测值"。工程已经为这条吃过教训
（写作台明确规定 `EstSec` 预估值不能进 `transcript.json` 当实测值用）——复盘页同规矩。

## 6. 与飞书的关系（要定死，否则是坑）

你原规范里飞书是数据中枢。现在要引入工作台，必须说清分工：

| 谁 | 干什么 |
|---|---|
| **工作台** | ★ **数据唯一真相**（`metrics.json`）+ 复盘页 + 报告 |
| 飞书多维表格 | **给人看/协作的副本**（跨项目汇总、与团队共享） |
| 同步方向 | 工作台 → 飞书（**单向**，R4 可选做） |

★ **不做工作台 → 飞书的反向同步**，理由与写作台那条同源：
「同一份数据不值得再付一次双向同步的代价」（`ScriptStore.cs:10-20` 注释已为此交过学费）。
**打开飞书改了数值 → 工作台不会知道**，界面要能让人知道这一点。

## 7. 风险登记（拟，待正式编号进 `优化与风险登记.md`）

| 拟号 | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R-新 | **录入坚持不下来**（这是复盘最大的死因——填一次很轻松，填五次就烦了） | 高 | ★ 字段**控制在 6~8 个**；提供"复制上次数据"；**天数满 7 天才提示**（不到期不催） |
| R-新 | **无结论的复盘**（填了数据没写结论 = 白填） | 高 | 保存时校验："已复盘"状态下结论不能为空 |
| R-新 | **预估值被当成实测值** | 中 | UI 上预估值**显式标灰**，绝不与真实抓取值并排 |
| R-新 | **样本不足就做排行** | 中 | 跨片排行留R3，且 <5 支片时显式写"数据不够" |
| R-新 | **画图手写代码量被低估** | 低 | 三类图共用坐标换算；不做通用引擎、不做交互式 |
| R-新 | **飞书那边也在改数值 → 两处不一致** | 中 | 界面明示"飞书是副本"；不做反向同步 |

## 8. 复用工程既有约定（照做，别重造）
