3B · 拆合随便拆，交棒才停下来

两个前提：① 所有交接只走「应用到下游」；② 交接有多贵，看项目的水位。拆合本身一律不打扰你。

前提一 · 交接闸门：没点「应用到下游」，下游一个字都不动

你定的规矩：所有环节都以「应用到下游」作为交接；回到上游修改，也要点它，下游才发生变化、才开始标「待重渲」。

分镜页现在恰恰没有这个按钮 —— 它是拆完 / 合完立刻落盘（SaveStageFiles()）。T-16 要补的就是它。

现在有真闸门的

① 粗剪页「应用到下游」→ 点了才让下游改用粗剪决策

精剪页「应用到下游」→ 点了才把精剪时间轴交出去

两页共用一个全局开关，顶栏常驻显示「下游使用：精剪 · 51 段 · …」

缺闸门的 / 假的

② 分镜页 —— 完全没有 ❌ ← 本次要补

④ 渲染页 —— 有按钮，但目前只是只读预览（宣布源 + 算 Δ），不是真交接 ⚠

⑤ 组接页是终点，不需要。

补上闸门之后，整件事就顺了：

拆 / 合  →  只改「草稿镜头表」，下游一个字都不动
     ↓
「应用到下游」  →  才把新表推给下游  →  此刻才：重排 + 改名 + 标「待重渲」

没点之前，下游读的还是上一版已交接的镜头表 → 根本不可能错位。
★ 所以那个「静默错位」的坑，不是靠"迁移做得好"来解的，是靠"压根还没交接"来解的。 迁移只是把交接那一刻做干净。

关键取舍：不禁止。灵感来了被系统拦住，比让你确认一次更烦。
要做的是把代价说清楚（几个产物要动、哪些设计要复核），然后自动擦屁股（改名 + 标记 + 可撤销）。
★ 水位决定的"贵"，从「拆的那一刻」移到了「交接的那一刻」 —— 拆随便拆，交棒时才拦你。这既兑现了"随意拆分没问题"，又保证下游永远只吃已交接的版本。

拆 / 合之后，设计怎么办（不再静默丢失）

拆分：一镜变两镜（只有两个选项）

① 保留原镜设计（默认）：原镜（前半）设计保留全文，打「待复核」橙标；新镜（后半）置空，打「待补设计」灰标。

② 彻底清空重新设计：两镜都清空，都标「待补设计」，交给 Agent 重做。

为什么删掉「按时间自动切分」这个选项：镜头的组成单元本来就是转写好的句子， 句子自带时间。拆镜头必然按时间切 —— 这是拆分的定义，不是选项。 原稿那个选项把「时间怎么切」（必然）和「设计怎么办」（要选）混成了一件事。而且"能不能自动切"取决于当初动效是怎么写的， 不取决于你现在想怎样 —— 这种选项不该摆给用户。

合并：两镜变一镜

默认两段拼接：a.设计 + "\n" + b.设计（画面 / 动效 / 配图 同理），打「待复核」。

为什么拼接合理：合并后这一镜的内容确实就是 a、b 两段连续的，拼起来恰好覆盖新范围（只是时间轴要重基）。

现状是 RemoveAt(pos+1) 一删了之 —— b 的设计直接蒸发，没有任何提示。

「待复核」只由你点「确认无误」清除，系统不自动清。 自动清 = 系统替你判断设计还够不够用，正是现状的毛病。
并发保护：Agent 正在跑设计时禁止拆合。另加一道保险 —— 任务包里带上「启动那一刻的镜头表指纹」， 回填时若发现镜头表已被改过，直接拒绝回填并提示「这份设计已作废，请重跑」。 （现状 FillVisuals 按镜号硬填，中途拆一镜就会整排错位。）

4C · 已经渲染完了，又回头拆镜头 —— 怎么办

这是你提的那个问题。答案已经定了：产物按镜号命名，文件跟着改名，方便人工回看。

先看好消息：这个坑已经被「交接闸门」关上了。 只要你没点「应用到下游」，下游读的还是上一版镜头表 —— 拆合改的只是草稿，产物不可能错位。 下面描述的是你点了交接那一刻要处理的事（也就是必须把文件搬干净）。
坑长什么样（没有闸门的话）。51 个镜头就像 51 个座位，每个座位挂一个号。你拆一镜 = 往队里插一个人， 后面全体往后挤一位。但只有座位号变了，磁盘上那 51 个文件一个都没动。 于是从拆点往后，每一镜读到的都是隔壁镜的画面：台词是自己的，画面是别人的。

而且它不报错。你点出片，软件照常跑完，吐一个整片错位的成片 —— 没有弹窗、没有红字。 而且现在的拆分/合并按钮根本不检查有没有渲染产物，一点就走。

这就是「文件跟着改名」这条路线的全部价值：不重渲，只改名。

算法骨架（拆 / 合各一次）

# 拆第 k 镜成两镜 ① 原镜 k ID 不变，镜号不变，DesignStale = true → 挂「待复核」 ② 新镜插入 k+1 分配新 ID，设计字段全空 → 挂「待补设计」 ③ k+1 之后的镜头 镜号 += 1，ID 全不变 ④ 算搬迁计划 [ { id:"s07", from:"shot_007.mp4", to:"shot_008.mp4" }, … ] ⑤ 执行 按「安全顺序」走（见下面坑 1） ⑥ 校验 按 ID + 指纹逐条核对 ⑦ 收尾 全成功 → 删计划文件；任一失败 → 按计划反向回滚，恢复原状 # 合并第 k、k+1 镜 ① 保留靠前那个（k）的 ID；k+1 的 ID 记进 mergedInto 后作废 ② k 之后的镜号 -= 1 ③ ④~⑦ 同上

三个最容易翻车的细节

1

改名必须倒着来

拆镜是「镜号变大」。若从前往后搬，shot_008 → shot_009 会盖掉还没搬的 shot_009，那个文件的原内容永久丢失。

镜号变大 → 从大号往小号搬；变小 → 反着来；省事就全部先改 *.tmp，搬完再统一改回（双缓冲，永不覆盖）。

2

ID 里不许带镜号

像 123a 这种不行 —— 镜号一变，123 就成了撒谎的历史遗迹（同一个 ID 迁移完挂到了别的序号上，看 ID 反而误导）。

用与位置无关的递增短码 s01 / s02 …，发号后永不复用。血缘另记：新镜 fromId（从谁拆出来），老镜 mergedInto（被并到哪去）。

3

只改「驱动流程」的文件

改：各种产物文件、shot-overrides.json、render-tasks.json。

不动：agent-response.json、prompt.md、apply-preview.json —— 它们是「当时发生了什么」的记录，改了就是篡改历史。

留痕文件里带上 ID 就够了：镜号后来怎么变，靠 ID 照样对得上，一个字不用改。

5你问的那个问题：算法和 ID 互相核验，对吗？

对，但要再加一个「指纹」 —— 你抓到了主干，只差一层。

手
算法

负责搬：重排镜号、算出每个文件该搬到哪、按安全顺序执行、失败时反向回滚。

干活的
钥匙
永久 ID

负责认人：这个文件是谁的产物。镜号怎么变都不会认错。

这是谁的？
证物
指纹

负责认版本：这份产物的内容还是不是当前这一镜那一版（台词/画面/动效/配图/时长的 sha1）。

是不是这一版？
为什么光有 ID 不够：ID 只能回答「这是第 7 镜的产物」。 但你可能回分镜页把第 7 镜的文案改了 —— ID 没变、文件没变，内容却过期了。 这时候要靠指纹比对：算出来的指纹 ≠ 清单里记的指纹 → 标「内容已变，待重渲」。

所以准确说法是：算法负责搬，ID + 指纹负责验。

一次拆合，三者在什么时候各干各的

步骤谁在动干什么
① 算计划算法 + ID按 ID 算出「谁搬到哪」，写成 reindex-log
② 执行算法按安全顺序改名（倒序 / 双缓冲）
③ 校验ID + 指纹逐条核对：这个名字下的文件，ID 对不对、指纹对不对
④ 判定指纹指纹一致 → 已就绪；对不上 → 待重渲
⑤ 兜底算法任一条不通过 → 按计划反向回滚，恢复原状
ID 的存活边界（这条容易想漏）：ID 不上门牌（不进文件名）—— 但必须活到渲染页。
否则渲染页只能看「文件在不在」：shot_004.mp4 在 → 报「已渲染」→ 其实是旧内容，静默错片。
有了 ID，能算出「第 4 位现在是 s03b，而 shot_004.mp4 的归属是 s04」→ 产物已过期。
一句话：ID 不上门牌，但入住要刷它。藏后台 ≠ 只在上游。

产物指纹清单长这样（新建 渲染产物\render-manifest.json）

{ "s07": { // ← 键是永久 ID，不是镜号 "shot": 7, // 渲染那一刻的镜号（仅供人看，会过期） "renderedAt": "2026-09-30T15:58:40+08:00", "fingerprint": "sha1(台词|画面构思|动效|配图|时长)", "file": "shot_007.mp4" // 改名时这个字段跟着改 } }

★ 键必须是 ID。如果键写成 shot_007，那拆合改名后这份清单自己就过期了； 用 ID 当键，镜号怎么变，清单永远对得上。
顺带把另外两个老问题一起拔了根：④ 渲染页的「状态」列现在只看「文件在不在」，有了指纹就能说「这份产物是旧的」； 改了文案/设计后，也能立刻知道哪些镜需要重渲（现在完全靠人记）。

9还有这些细节待敲定（这一轮新查出来的）

不是决策点，是实现时会踩到的具体问题。先摆出来，免得开工才发现。

A

重切分会把「永久 ID」洗掉。 BtnResplit 是重建整张镜头表 —— 按现在的实现，所有镜都是新对象，ID 会全部重发，那「永久」就不永久了。 建议：明确「重切分 = 推倒重来」，ID 全部重发、产物全部作废，并在确认框里说清。

B

补发 ID 必须「只给空的补」。 老项目打开时 ShotRow 没有 Id 字段，如果每次打开都发一遍新号，ID 天天变 = 白做。 规则：只在 Id 为空时发号，发完立刻回写；shotlist.json 会自动带上（它整份序列化 _s.Shots）。

C

拆分点是「句末」，不能任意指定。 现状只能在最接近中点的句末切，而且要求这一镜内 ≥ 2 句（否则直接拒绝）。 问题：卡片流里要不要给「切在第几秒 / 第几句」的选择？还是先保持现状？

D

字典类文件的键，建议直接用 ID。 比如 shot-overrides.json 现在是按镜号存。若改成按 ID 存，拆合时一个字都不用改， 比「跟着改名」更省事、更安全。代价：文件可读性略降（要对着清单才知道 s07 是第几镜）。

E

成片（L3）过期没有标记。 拆合后成片还躺在 stages/05-assemble/ 里，只有一句提示，文件本身没标识。 建议同样做一份 assemble-manifest.json（记成片用的镜头表指纹），对不上就打「已过期」。

F

「待重渲」的镜怎么一键重渲？ 拆合会产生 1~2 镜待重渲。④ 渲染页现在有单镜重渲（agent-reshoot）。 建议：卡片上的徽章点一下，直接带上镜号跳到 ④ 页。

G

render-tasks.json 重新生成会不会冲掉你在 ④ 页调的参数？ 它是「整份按新分镜表重新生成」，而你在 ④ 页对某镜的覆盖设置存在 shot-overrides.json 里。 实现前要确认生成时会不会读回 overrides —— 不读的话拆一次合就把 ④ 页的调整抹了。

H

水位判断要扫盘，别每次点都扫。 判 L2 要列 渲染产物\ 目录、判 L3 要列 05-assemble\。 建议：进页面时算一次 + 操作后更新，不要每次点按钮都重扫。
