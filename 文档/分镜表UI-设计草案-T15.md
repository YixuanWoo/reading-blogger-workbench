## 一、现状：实测（不是感觉）

控件是 **WPF `DataGrid`**（`Step2ShotView.xaml:270` `x:Name="GridShots"`），8 列，一格一镜。

**真实宽度账**（主窗口默认 1500×900，左侧导航 204，页面 Margin 16×2，左栏口播稿 380+10）：

```
右侧分镜区可用宽度 = 1500 − 204 − 32 − 390 ≈ 874 px
  ├─ 固定窄列：#34 + 编辑34 + 起点52 + 时长44 + 文案140 = 304 px
  └─ 伸缩列剩 570 px，按 2* / 1.7* / 0.8* 摊（共 4.5 份 ≈ 127 px/份）
       ├─ 画面构思（场景）  ≈ 253 px   → 约 11 个汉字/行
       ├─ 动效（逐段时间线）≈ 215 px   → 约 9 个汉字/行
       └─ 配图             ≈ 101 px   → 约 4 个汉字/行
```

**而这三格的典型内容是段落级的**，例如动效：「0-3s 标题淡入居中 / 3-6s 图1 左侧推入、文案右侧淡出 / 6-9s 数字从 0 滚到 100」。215px 宽塞这句 = 换行 5~6 行，行高被撑到 150px+，还和上下行抢视口。

## 二、问题清单（每条都指到代码）

### D1 · 「文案」列是死的，而且硬截断
`ShotVm.DisplayText`（`Step2ShotView.xaml.cs:1455`）是 **get-only**：

```csharp
/// <summary>表格里显示的文案。太长就截断，省得一行占满屏幕。</summary>
public string DisplayText =>
    Model.Text.Length > 46 ? Model.Text[..46] + "…" : Model.Text;
```

两个后果：
1. **改不了**。`DataGridTextColumn` 的 Binding 默认 TwoWay，绑到只读属性 → 编辑不生效（写不回去）。这一列在界面里其实**根本没有编辑能力**，只能去左边「成片口播稿」改。
2. **看不全**。这列**没有** `TextWrapping`（只有后三列设了 `ElementStyle` 的 Wrap），140px 里那串 46 字**被裁剪**，实际只看得见前 9 个字左右。

→ 这就是用户体感最直接的来源：**"镜头的台词一行都不够"**。

### D2 · 编辑态一律单行 TextBox ★ 核心
全表**没有任何一列设 `EditingElementStyle`**（全项目只 `Step4ExportView.xaml:140` 有一处，还是给「微调帧」那个数字框）。

所以四个文本列的编辑态都是 WPF 默认单行 `TextBox`：**回车即提交并跳走、不能换行、没有 Wrap、内容长了横向爬**。写「动效」这种多段文本时，等于在一个单行输入框里写小作文。

→ 这就是用户要的**"要设计成文本框"**。表格给不了这个，这是 `DataGridTextColumn` 的天花板。

### D3 · 列宽与内容形态错配
四个窄列（#/起点/时长/文案）吃掉 304px 固定宽度，其中「文案」140px 只用来看前 9 个字；真正需要宽度的三个段落列只剩 570px 分。**表格范式把"文档"硬塞进"格子"**。

### D4 · 行高无上下限
`RowHeight="NaN"`（自适应）是唯一的行高设置，没有 `MinRowHeight` / `MaxRowHeight`。内容一长，某行能撑到几百像素，**表头滚出视野**，看不见列名。

### D5 · 不是 ObservableCollection，行模型也不通知
`_vms` 是 `List<ShotVm>`（`:54`），刷新靠 `ItemsSource = null; = _vms;`（`:1168-1169`）整表重建；`ShotVm` 也没实现 `INotifyPropertyChanged`。
→ 单元格改完值，**表内其他联动不会自动刷新**。这次改造如果要做"边打字边显示字数/联动提示"，必须顺手解决。

### D6 · 「文案」是派生数据，可编辑会引出冲突
`ShotRow.Text` 不是手写的，是**切分时按时间范围把口播稿的句子拼出来的**（`:626` `Text = sp.Text`；合并时 `a.Text + " " + b.Text`；拆分时按 `StartSec` 切句子拼）。
→ 一旦允许在分镜表里手改台词，就要回答「跟左侧口播稿谁说了算」「重切分会不会覆盖」。现有机制里有现成先例可沿用：`Edited` 标记（手动调过的镜头重切分前弹确认）。**这是要用户拍板的决策点，见 §七。**

## 三、设计目标与不变量

**目标**
1. 镜头台词、画面构思、动效、配图 —— **四个字段都能在分镜页直接多行编辑**，不再借道左侧口播稿。
2. 一屏能看清"这一镜要发生什么"，**不用来回点选**。
3. 密集浏览（连着看几镜的动效节奏）仍然快。

**不变量（改完必须还成立）**
- `project.json` / `shots` 结构**一个字不改**，旧项目打开即用。
- 四个字段的落盘链路不变：仍写 `ShotRow` → `SaveStageFiles()`。
- 现有关键按钮全部保留：合并选中镜+下一镜 / 拆分选中镜 / 重新自动切分 / 交给 Agent 设计画面 / 保存分镜表。
- `Edited` 标记语义不变（✎ + 重切分前确认）。
- 与 Agent 回填（`Description`/`Motion`/`Image` 被 Agent 改写）的兼容不变。

## 四、三个候选方案

### 方案 A —— 就地小改（保留 DataGrid）
只做四件事：① 文案列改成可编辑（加 setter）且显示换行；② 给四个文本列加 `EditingElementStyle`（多行 TextBox）；③ 列宽重排，窄列收拢；④ 行高加上下限 + 表头固定。

- ✅ 改动最小、风险最低，可当天完成；表格的"扫一眼对比多镜"能力保留。
- ❌ **治不了根**：874px 里 8 列，段落文本的可用宽度还是只有 200-250px；`DataGrid` 的单元格编辑态天生别扭（编辑框高度、滚动、Tab 走位都要手工调）。
- 一句话：**把表格做得不那么难受，但它还是表格。**

### 方案 B —— 卡片流（一个镜头一张卡）★ 推荐
`DataGrid` → `ItemsControl` + 卡片模板。**"一行"只留给元信息**（镜号/时间/时长/✎/快捷按钮），四个文本字段各占一块多行编辑区。

- ✅ **根治**：段落文本拿到整卡宽度（约 830px，是现状的 3~4 倍），行高随内容自适应（3~10 行封顶）；
- ✅ 视觉上"一镜一块"，跟"分镜是文档不是表格"的本质对齐；
- ✅ 可以顺手加"折叠"——折叠后每镜只剩元信息一行（**密集模式**），展开就是编辑模式。一箭双雕。
- ❌ 改动较大：XAML 重写、`ShotVm` 要上 `INotifyPropertyChanged`、选中/按钮可用性逻辑要重接；
- ❌ 默认状态下单屏可见镜头数变少（1500×900 大约 6~8 张展开卡；折叠后 20+）。

### 方案 C —— 主从（左紧凑列表 + 右编辑表单）
左边一个极窄列表（每行：镜号 + 时长 + 台词前 12 字），右边是选中镜的完整表单（四个大文本框）。

- ✅ 列表密度最高，长文本编辑空间最大。
- ❌ **必须点选才能看内容**。做"连着看 5 镜动效是否连贯"这种节奏检查时，要一次次点、一次次读，很累。
- ❌ 和左侧已存在的「口播稿」面板形成**左右左三栏**，信息架构变复杂。

### 对比

| | A 就地小改 | **B 卡片流** | C 主从 |
|---|---|---|---|
| 段落文本可用宽度 | ~250px | **~830px** | ~600px |
| 多行编辑 | 凑合（单元格内） | **原生** | 原生 |
| 一屏看几镜 | 8~10 行 | 6~8 卡（折叠 20+） | 列表 20+ / 详情 1 |
| 来回点选 | 不用 | 不用 | **频繁** |
| 改动量 | 小 | 中 | 中大 |
| 根治程度 | 缓解 | **根治** | 根治但有新代价 |

**推荐 B**，并吸收 A 的优点（元信息保持一行、扫读快）和 C 的诉求（提供折叠开关切换密度）。

### 5.3 交互

| 动作 | 行为 |
|---|---|
| 打字 | **实时写回 `Model`**（与左侧口播稿一致，无需"保存"按钮；`SaveStageFiles()` 落盘沿用现有触发点） |
| 换行 | `Enter` 正常换行（`AcceptsReturn=True`） |


## 附：为什么这件事值得改

分镜页是**唯一一个"人在里面做创作决策"的页面**——第①②④⑤步都是机器在算，只有第③步是人在写"这一镜到底要发生什么"。

而当前 UI 给创作内容的配额是：**动效 215px、画面构思 253px、配图 101px**。
这不是"不太好用"，是**这一页最重要的东西被安排在了最小的格子里**。
