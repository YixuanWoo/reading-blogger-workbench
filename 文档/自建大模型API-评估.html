工作台要不要自己接大模型 API？

结论先说：值得做，但真正的收获不是"变成私人 agent"，而是把那条又长又脆的叫醒链路换掉。

六步流水线里，只有 3 处真的需要大模型。
自建 API 不是重写工作台，是给这 3 个点接一条线。
而且这条线的成本，一部片子只有几毛到几块钱 —— 钱从来不是障碍。

1先看清：谁真的需要模型

整条链的主体是本地 ffmpeg 和 HyperFrames 在干活，模型只出现在三个点上。

写稿你写 Markdown
转写语音 → 文字（ASR）
精剪你定切点
分镜设计创意活，最吃模型
渲染HyperFrames 本地
出片组接ffmpeg 本地

要调用大模型（含"单镜重渲"这类改 HTML 的活，也要代码模型）　　纯本地，和模型无关

2自建 API 能治什么病、治不了什么

现在的链路是：工作台 → 桥接进程 → 网关 → 你的会话，绕四道弯，三道弯上都有已知故障。

能治（都是真痛）

  • 桥接进程死了不会自己重启，得重开工作台
  • 会话正忙时，唤醒消息会被"悄悄丢掉"（界面还显示成功）
  • 网关端口和密码每个会话都变，凭据容易过期
  • 干活的时候 WorkBuddy 必须开着

治不了（别抱期望）

  • 它不会让工作台"变聪明"。调 API 只是让工作台变成"客户端"；真正的 agent 能力（自己看文件、多步推理、试错重来）还得另写一层编排代码，那才是活
  • 你只是换了个依赖：从依赖 WorkBuddy，变成依赖某家模型厂商
  • 新增一堆要长期维护的东西：Key、计费、限流、重试、模型版本升级

3成本：先算笔账

按一部片子 219 个镜头算，每镜约 3K 输入 + 1K 输出 → 约 66 万输入 / 22 万输出 token。

用哪一档模型一整部片子的花销
便宜档（qwen3.7-flash 一类）约 0.3 元
主力档（DeepSeek Flash 一类）约 1.5 ~ 3 元
旗舰档（DeepSeek V4 Pro 一类）约 6 ~ 15 元

转写那一步更便宜，按音频小时计费，不走 token。
价格是 2026 年 9 月的行情，会变；真要动手前重新核一次价即可。
结论：成本从来不是理由。真正该决定的是下面这个岔路。

4我的建议：分四期，别一次做完

每一期都能单独用上，而且每期都不破坏现有功能。

1
启用已有的「直连大模型」通道几乎是零成本

代码和设置界面都已经写好了（见 §10）—— 只要在分镜页的 Agent 设置里填上 接口地址 / Key / 模型名，点一下「检测连接」。原来的"任务包 + 桥接"通道原样保留当备胎，随时切回来。

2
转写改接专用语音服务

这一环最独立、最干净，也最容易被当成"顺便"做的事。注意：它该用语音识别服务，不是聊天模型。

3
分镜设计 + 单镜重渲接代码模型

这才是"创意活"，也是最挑模型质量的一步 —— 想清楚用哪家，比想清楚要不要做更重要。

4
到这一步，才谈得上"私人 agent"远期

前面三期做完，"工作台自己就能干活"这件事才真正成立。

5关键岔路：你要的是"隐私"还是"独立"？

这两个目标听起来差不多，但通向完全不同的技术路线。这一步定不下来，后面都是白做。

隐私优先

素材、稿子、录音一个字都不出本机。

代价：得用本地开源模型，创意类工作质量会明显下降，还要求显卡

独立优先

不受订阅束缚、随时能干活，效果要够好。

代价：还是依赖模型厂商，只是从"依赖 WorkBuddy"换成"依赖它"

也可以混合：简单的、敏感的活走本地，创意活走云 —— 这是最实际的第三条路，但要多写一层路由逻辑。

6顺带说一句：还有反方向的路

今天讨论的是「工作台 → 调 AI」。还有一个反方向：「AI → 遥控工作台」（MCP 那条，评估文档已经写好了：MCP控制工作台-可行性评估.html）。

两个方向不冲突，是互补的 —— 前者解决"没人干活的时候它自己把活干了"，后者解决"我想验收的时候，AI 能自己点界面、自己看结果"。

7一个必须先拆开的误会

"工作台要能调用本地代码 / 服务，才算有 agent 能力" —— 这句话把两件完全不同的事混成了一件。

听起来像同一件事实际是什么你的工作台
能调用本地代码 / 服务 普通程序就会做的事 —— 这是个"接口"问题 早就会了：ffmpeg 的解码 / 量时长 / 出片组接 / 导出都是它自己跑的；node 只用来启动桥接
有 agent 能力 自己决定"下一步该干什么" —— 这是个"判断力"问题 没有，而且不需要它有

你担心的是前者，真正难的是后者。而后者你已经有了 —— 就在这场对话的另一端。
工作台是一双熟练的手：你告诉它切哪、渲哪个、怎么拼，它都又快又准。它缺的不是手的能力，是"没人指挥时自己拿主意"。那个拿主意的人，不用你造，已经有了。

8你的三个担心，逐条回答

"难度大不大 / 工程多不多 / 维护难不难" —— 完全取决于选哪条路，而这三条的差距是数量级的。

路线工程量维护难度以后谁来修结论
工作台自带推理工作台里塞一个会自己试错的大脑 极大而且是无底洞 极高 全是你自己还得追着模型升级跑 不该做
只接模型、出文字一次问答：发请求 → 收 JSON → 写盘 小百行级 中低 代码我改模型和提示词你改配置 可以做
手归手、脑归脑工作台干活，Agent 拿主意 中重点是把接线做稳 最低 最难的那半WorkBuddy 那边在维护 最推荐

你怕得对：第一行那个"工作台自带推理"，确实是个无底洞 —— 因为它不是一个功能，是一整个产品。
想想我干活时要处理多少事：先看哪个文件、命令失败了要不要换招、跑太久要不要停、上下文太长怎么删、模型今天抽风了怎么办……这些没有一行是"写完就不用管"的，得跟着模型一起演进。这就是为什么做 Agent 的公司是几百人的团队。
好消息是：你根本不需要走那条路。

9让"以后好维护"变成真的：三个抽屉

规则只有一条 —— 会变的放抽屉 1，不太变的放抽屉 2，最难的放抽屉 3（别自己造）。

抽屉放什么谁来改怎么改
1 · 配置 模型名字、API 地址、提示词、价格档位 你自己 改一个文本文件，不用碰代码
2 · 代码 界面、ffmpeg 参数、状态机、产物管理 我 改完重新打包
3 · 别人的 模型推理循环、工具调度、上下文管理 WorkBuddy 你什么都不用管

这个分法的目的很具体：让你以后需要动手的，只剩下"改一个文本文件"。
你不是工程师没关系 —— 剩下两种活，都不用你干。

10更正 + 一个好消息（翻过源码之后）

用户当场指出我上面说错了一处。翻完源码：他是对的，而且顺着这条线挖出一个更好的消息。

① 更正：HyperFrames 逐镜渲染，确实不是工作台干的

本地能力到底谁在干代码证据
ffmpeg 解码音频 / 量时长 工作台自己 FFmpegDecoder.cs 用 Process.Start 起 ffmpeg
出片组接（拼片 + 混音 + 编码） 工作台自己 FFmpegAssembler.cs 调 FFmpegExporter.RunProcess(ffmpeg, …)
启动桥接 工作台自己 AgentBridge.cs 起 node.exe 跑 bridge.js
HyperFrames 逐镜渲染（HTML → MP4） Agent（我） 所有 .cs 里 "HyperFrames" 都只是路径 / 枚举名 / 提示词文本，没有一处 Process.Start；维护说明.md 第八节把它明确列为"外部引擎"

准确的说法是：工作台自己会调 ffmpeg（而且是最难的组接环节），但不会自己跑渲染。上一版把 HyperFrames 也算进"工作台在调"，是我说错了。

② 好消息：「工作台直连大模型」这条路，代码里早就写好了

AgentBridge.cs 开头就白纸黑字写着两条通道，而且界面上是一套用法：

通道什么时候走这条现状
① 直连大模型OpenAI 兼容的 /chat/completions，支持流式 配置里填了 接口地址 + Key + 模型名 代码已就绪，但从来没填过 Key
② 任务包文件写 agent-request.json，等外部 Agent 回包 没填 Key 时自动走这条 一直在走这条（也就是"桥接"）

更好的是：设置界面也是现成的 —— AgentSettingsDialog（从分镜页能打开），有「接口地址 / API Key / 模型名 / 流式开关」四个输入，外加一个 「检测连接」按钮。里面模型名给的例子就是 deepseek-chat / gpt-4o-mini / 本地模型名。
配置落在 %APPDATA%\翊瑄的工作台\config.json。

所以"工程量"比上一版估的还小：
不是"要开发"，是"填三个值 + 按一下检测连接"。
它管的是"出文字"那类活（分镜设计、单镜重渲）。渲染那一段不在其中 —— 而渲染恰恰是最不该塞进工作台的那一段。

为什么渲染不该塞进去：它要跑脚本、要排查"零报错的静默失败"、要改 HTML 反复试 —— 全是判断力活。工作台擅长的是"有确定答案的事"（切点、拼片、混音、算指纹），判断力活交给 Agent。
这条分工线，代码里其实早就划好了。

一句话决策建议：先去分镜页打开 Agent 设置，填 接口地址 / Key / 模型名，点「检测连接」—— 你立刻就能感到差别。
再送一句定心的：你怕的那个"无底洞"，恰恰是唯一一条你不需要走的路。
