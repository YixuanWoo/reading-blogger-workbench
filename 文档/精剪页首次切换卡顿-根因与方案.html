精剪页首次切换卡顿 / 崩溃

根因定位 · 实测数据 · 修复方案　｜　2026-10-03　｜　针对 WaveformControl.LoadPeaks
已定位到单点 有实测数据支撑 改动局限在 1 个文件
一句话结论：不是"首次加载东西多"，是在界面线程的绘制函数里同步解码了整个源音频文件。 你的源素材 652 秒 ≈ 1.7 秒卡死；同时后台预热线程在解同一个文件，两条线程抢解码器。 第二次切换不崩，是因为峰值缓存命中了，一行代码都没执行。

一、故障链路

STEP 1
点「精剪」
首次进入才创建 EditorView，铺 108 个块（你的项目实测日志）
STEP 2
绘制波形
每个块调 LoadPeaks，缓存未命中 → 开解码器读完整文件
STEP 3
UI 冻结 1.7 秒
绘制函数里同步解码，界面完全无响应，看起来像崩了
STEP 4
叠加预热线程
后台同时解同一文件，内存与解码器争抢 → 真正崩
STEP 5
第二次切换
缓存命中，0 毫秒 —— 所以"重启第二次就不崩"

二、代码上的三个问题（互相叠加）

问题 1（主因）：在 OnRender 里同步解码整个文件

WaveformControl.cs:872-880 —— DrawClipWaveform 是个纯绘制函数，却在缓存未命中时直接调 LoadPeaks：

private void DrawClipWaveform(...)
{
    if (!_peakCache.TryGetValue(clip.SourcePath, out var peakData))
    {
        peakData = LoadPeaks(clip.SourcePath);   // ★ 在界面线程解整个文件
        ...
    }

而 LoadPeaks（:933）做的事是：new AudioFileReader(path) → 逐样本读到文件结尾 → 每 100 个采样点记一个峰值。它不管当前视野只用到其中几个像素。

绘制函数必须"要么有数据、要么什么都不画"，绝不能在里面干活。这是 WPF 的硬规矩。

问题 2：后台预热被触发 108 次，和 UI 线程抢同一个文件

EditorView.xaml.cs:118 把预热挂在 _project.Changed 上；LoadPreCutProject 铺块时每加一个块就 AddClip → NotifyChanged()（TimelineProject.cs:77）。

108 个块 = 108 次事件。虽然有 400ms 防抖，但最后一次必然触发，于是 TimelineAudioRenderer.Render 在后台线程又开一个 AudioFileReader 解同一个 m4a。

m4a 定位很贵（工程注释里实测过 ±42ms 且方向不定），两条线程同时抢 MediaFoundation 解码器，内存峰值直接翻倍。

问题 3：SetProject 重复挂事件处理器（顺手发现的隐患）

WaveformControl.cs:117 —— SetProject 每次调用都 _project.Changed += ... 加一个新委托，旧的从不摘掉。而它被调了 4 次（EditorView.xaml.cs 的 111 / 517 / 555 / 637）。

同一个 TimelineProject 被反复 SetProject，于是"内容变了"会引发 N 次 InvalidateVisual。InvalidateVisual 本身便宜，但 N 份 Changed 处理器意味着后面任何优化都要乘 N。

三、实测数据（本机，真实 m4a 素材）

用工程里那份 NAudio 2.2.1 + 同一份 LoadPeaks 原样复刻，跑真实素材：

操作素材时长实测耗时
GetDurationSec（只读时长）285 秒291 ms
LoadPeaks（读全文件算峰值）285 秒748 ms
LoadPeaks 第二次（无缓存）285 秒748 ms
按比例推算到你的 652 秒素材652 秒≈ 1.7 s

这就是"卡顿"的全部：1.7 秒里界面线程 100% 被占住，什么都画不出来、点不动。
用户视角 = "点一下就卡死 / 好像崩了"。而"崩溃"是第二步 —— 叠加后台预热线程后内存峰值翻倍，或 WPF 渲染超时被系统判为未响应。

四、为什么第二次切换就没事

_peakCache（WaveformControl.cs:40）是实例字段，而 WaveformControl 活在 EditorView 里，编辑器是 KeepAlive 的（NavTree 里只有精剪页 KeepAlive = true），切换时不销毁。

→ 第二次进来时 TryGetValue 命中，0 毫秒解码。缓存甚至和项目同寿命，所以"同一个会话内第二次永远不卡"。

但这不是修复，是把问题推迟了：换一个项目、关掉再开，缓存就没了，同一场卡顿会原样再来一次。所以必须动代码。

五、修复方案

修法 1（必须做）：把峰值计算挪出绘制函数，丢到后台

三步走：

  1. 绘制函数只读缓存，绝不解码。缓存没有 → 这一帧就不画波形（块仍是实心的），立刻返回。
  2. 新增一个静态的"后台峰值任务"：Task.Run 里解码，结果写进带 lock 的字典；WaveformControl 订阅"算好了"通知 → InvalidateVisual() 补画一次。
  3. 同一路径只解一次。用 ConcurrentDictionary + Lazy<Task>，或一个 _loading 集合，保证 108 个块指向同一文件时只开一个解码器（现在靠 TryGetValue 侥幸没重复，一旦改成异步就必须显式去重）。

效果：界面立刻可交互，波形在 1.7 秒内自己补齐。用户看到的是"波形慢慢长出来"，不是"卡死"。

修法 2（强烈建议）：铺块期间别触发音频预热

LoadPreCutProject / RestoreTimeline 批量加块时，Changed 会发 N 次。改法二选一：

  • 加"批量模式"开关：BeginBatch() / EndBatch()，批量期间不发 Changed，结束时发一次。
  • 更省事：铺完块再手动调一次 ScheduleAudioPrewarm()，并在这两个方法期间"静音"事件。

收益：预热只跑一次、且在铺块完成后才启动 → 不与 UI 线程的峰值解码抢同一个文件。

修法 3（顺手，2 行）：SetProject 先摘旧处理器

public void SetProject(TimelineProject project)
{
    if (_project != null)   // ★ 先摘掉旧的，否则挂几次就叠几层
    {
        _project.Changed -= _onProjectChanged;
        _project.SelectionChanged -= _onSelectionChanged;
    }
    _project = project;
    _project.Changed += _onProjectChanged;
    ...
}

要把 lambda 提成命名字段才能 -=。这属于第 5.1 节记的那类"重复挂载"隐患，顺手清掉。

修法 4（可选，最彻底）：峰值缓存提到进程级

_peakCache 现在跟着编辑器活。把静态峰值缓存提为进程级（按 文件路径 + mtime + 大小 做键），收益：换项目、重开工作台、编辑器和别处共用同一份 → 永远只解一次。

成本：要管缓存上限（比如最多 8 份、超了就按最后使用时间淘汰），否则大项目会把内存吃住。

六、改动清单与验收

文件改什么风险
WaveformControl.cs修法 1（异步峰值）+ 修法 3（摘旧处理器）低 — 只影响绘制与缓存
EditorView.xaml.cs修法 2（批量模式）低 — 只影响事件时机
TimelineProject.cs（可选）修法 4（进程级峰值缓存）中 — 涉及缓存生命周期

验收判据（每条都要有数字，不能靠"看起来不卡"）

  • 首次点「精剪」→ 界面在 200ms 内可交互（现在约 1700ms 冻结）。
  • 波形在 1.5~2 秒内自动补画完整，不需要用户做任何操作。
  • 整个过程日志里没有内存异常；任务管理器里工作台内存不出现双倍尖峰。
  • 切走再切回 → 波形立即在（0 毫秒，和现在一样）。
  • 换一个新项目重复上述 1~3 条 → 仍然流畅（这条验的是修法 1 的去重逻辑）。
  • dotnet build 工作台\工作台.csproj -c Debug → 0 警告 0 错误。

一句话验收：把日志里那行 [INFO] 工作台交接：108 段保留区间，铺开总长 200.4s 的前面补一条时间戳，再补一条"峰值就绪"的时间戳 —— 两行之差就是卡顿的真实时长，改完应该小于 200ms。
