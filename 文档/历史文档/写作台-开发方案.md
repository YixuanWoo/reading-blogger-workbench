## 0. 一句话结论

**写作台 = 项目内流水线的「第 0 步」**，摆在「音频粗剪」之前，编号 `0`。
现有 1~5 一步不动、不重编号（重编号会让老项目的肌肉记忆和截图对不上）。
导航从「平铺 6 项」升级为「**三组：文稿 / 成片 / 资源**」——因为 7 项只是临界点，
加上期二录音台、期四看板就是 9 项，**现在改最便宜**。

## 1. 位置：为什么是「项目内」

### 1.1 判据

| 候选 | 判据 | 结论 |
|---|---|---|
| **项目内** | 稿子属于**某一支片**（`项目\<名>\script.md`） | ✅ 采用 |
| 全局 | 稿子属于"我"，像书单那样跨项目 | ❌ 否 |

★ 这条判据和《阅读管理页规划》用的是**同一把尺**（「书单不属于某一支视频 → 全局」），
两页的归属逻辑因此自洽，不打架。

### 1.2 为什么不插进 1~5 中间

它**不是**流水线的一环，它是 ① 的**上游**：`script.md` → `transcript.json` → 粗剪。
插在 1 和 2 之间会暗示"粗剪完才开始写稿"，那是倒着。

### 1.3 ★★ 三个新发现的坑（规划稿里没写，必须现在定）

####坑 1：默认落点要按「立项模式」分流，不能写死

现状（`NavTree.cs:152`）：

```csharp
public static string DefaultProjectId => Ids.StepCut;   // 写死永远是粗剪
```

写作台加了之后这条会**变成一个真 bug**：
打开《思辨与立场》这种**录音驱动**的老项目，它已经做到成片了，落地却弹到写作台（空的），
用户以为稿子丢了。

正确做法（把它从常量改成函数）：

| 立项模式 | 打开项目落在 |
|---|---|
| `script`（文稿驱动·新） | **写作台**（一切从这里开始） |
| `recording`（录音驱动·老，默认） | **音频粗剪**（保持现状，一个字不变的老路） |

★ 迁移规矩照抄铁律：**老项目只给空的补默认，不改已有值**——`ProjectRef.DriveMode`
默认为 `recording`，老档案反序列化出来就是 `recording`，天然零改动。

#### 坑 2：`ShotPart.ScriptText` 已经存在，名字会撞车

实测（`ProjectModel.cs:166`）：

```csharp
/// <summary>降级用的文案稿（没导入转写稿时，口播稿由它按字数占比估算）。</summary>
public string ScriptText { get; set; } = "";
```

它已经在 ③ 分镜里当**兜底文案**用了。如果写作台的数据模型也叫 `ScriptText`、
或者也写成"稿子"，将来必然出现两个"稿子"字段打架。

★ **定死口径**（照"产物认ID 不认镜号"那套思路）：

| 名字 | 是什么 | 谁写 |
|---|---|---|
| `script.md` / `ScriptBlock` | **稿源**，人写的原文，唯一真相 | 写作台 |
| `transcript.json` / `Transcript` | **带时间的稿**，下游吃这个 | 写作台导出 或 外部 Agent |
| `ShotPart.ScriptText` | **成片口播稿**，由前两者推出来的**派生物** | 精剪/分镜 |

→ **新代码一律不许叫 `ScriptText`**，写作台的模型叫 `ScriptDoc` / `ScriptBlock`
（规划稿已用这两个名，恰好避开了，是对的，保留）。

#### 坑 3：`01-transcript` 现在是**空目录**，别当成"已支持转写"

实测 `项目\AI时代读书的价值\stages\01-transcript\` 是**空的**（0 个文件）。
`transcript.json` 由**外部 Agent** 交付（粗剪页"复制转写提示词"那条路）。

→ 这不影响方案（写作台是**生成方之一**，不是消费方），但写文档时**不要**说
"工作台已支持 transcript.json"，它目前是纯外部产物。

## 2. 导航结构设计

### 2.1 目标形态

```
【全局】没打开项目（保持原样，一字不改）
   ✦ 灵感
   ▤ 进行中
   ▥ 已归档
   （未来：阅读管理 —— 跨项目个人数据，另有规划）

【项目内】打开项目后
   ── 文稿 ────────────────────
   0  写作台            ← 新增
   ── 成片 ────────────────────
   1  音频粗剪
   2  精剪
   3  分镜设计
   4  渲染
   5  组接导出
   ── 资源 ────────────────────
   ▤  素材库
```

★ **1~5 的数字和顺序一个都不动**。只在最上面插入 0。
（重编号的代价：老项目截图、文档、用户记忆里的"第3 步"全部对不上，收益仅是"编号连续"。）

### 2.2 实现：只加一个 `Group` 字段，不做二级菜单

`NavNode`（`Navigation/NavNode.cs`）加一个字段：

```csharp
/// <summary>
/// 分组名（"" = 不分组）。同名的连续节点会画一条分隔线 + 组标题。
/// 只做"视觉分段"，不是二级菜单（NavHost 不画缩进、不做子项展开）。
/// </summary>
public string Group { get; init; } = "";
```

`NavHost.Render`（`Navigation/NavHost.cs:67` 的 `foreach`）里，遍历时记一个
`lastGroup`，组名一变就插一个分隔控件。约 25 行。

| 文件 | 改什么 | 行数 |
|---|---|---|
| `NavNode.cs` | 加 `Group` 字段 | ~6 |
| `NavTree.cs` | 各项填 `Group`；`DefaultProjectId` 改函数 | ~30 |
| `NavHost.cs` | 组变化时插分隔线 | ~25 |

★ 节点模型和渲染是分开的（`NavNode.cs` 注释里明说了"不关心怎么画"），所以加组不牵连业务。

### 2.3 落点与记忆

- `DefaultGlobalId` = `ProjectsActive` —— **不动**。
- `DefaultProjectId` → 改成 `DefaultProjectId(DriveMode)`（见坑 1）。
- `PickLanding` 的兜底逻辑不动：跨作用域记忆会退到该作用域的默认落点。

### 2.4 顺手能解决的：跨页提醒

七项里最该被看见的是"**有稿子改了，但没导出**"。建议在写作台那一项上用**已有的**
`Badge` 字段（`NavNode.cs:63`，现成能力）显示 `待导出` 角标，切换作用域时重算。
不新增任何机制。

#### 3.1.2 三栏骨架

见 §3.2（三栏示意 + 为什么左栏是"大纲"而不是"段落列表"）。

#### 3.1.3 ★ 三处 UI 细节（都是踩过的坑变的）

**① 「预估」和「实测」必须视觉上分得开**（防坑：预估值伪装成实测值）

| 状态 | 徽章 | 时长显示 |
|---|---|---|
| 已录 | 绿色 `已录 18.4s` | `实测 18.4s` |
| 未录 | 灰色 `未录音` | `预估 21.1s` + 详情栏黄字警告「不准」 |

★ 未录音段落测出来的是**字数 ÷ 4.2 字/秒**的估值。这个数**永远不能进`transcript.json`
当实测值用**，导出时它被标成 `Engine="script"` 且页面上显式标灰。

**② 「待重录」会自动亮起来**（改稿联动的可见性）

改了某段正文 → 该段卡片左边框变**琥珀色** + 徽章变「待重录」+ 录音状态清空
（因为旧录音已经和稿子对不上了）→ 底部统计的「N 段待重录」跟着变。

★ 这条链路就是**写作台与录音台共用同一份 `ScriptBlock`** 的可见证据——
用户能亲眼看到"改了稿，录音就作废了"，而不是两套数据各说各话。

**③ 「应用到下游」放在详情栏最下方，并且带警示框**

直接抄你定的那条铁律：**没点 = 下游读的还是上一版**。
原话写进警示框，不做委婉措辞——因为这是最容易忘、又最致命的一条。

#### 3.1.4 导航栏里的写作台项（原型左侧可见）

── 文稿 ──

```

★ 角标用**已有的 `Badge` 能力**（`NavNode.cs:63`），不是新机制。
「待导出」= 稿子改过但没导出 transcript.json——这是最该被看见的状态。

#### 3.1.5 操作按钮（照抄现有键名）

### 3.2 ★ 三栏骨架与卡片流

（原型见 `文档\写作台-UI原型.html`；色板与按钮样式键见 §3.2）

```
┌────────────┬─────────────────────────────┬──────────────┐
│ 大纲树236px │  段落卡片流（主区，flex）      │ 段落详情 340px │
│ · 段ID     │  · 卡片：ID + 状态章 + 正文      │ · 正文编辑框│
│ · 句数时长 │  · 底栏：永久ID / 重录遍数 / 状态│ · 状态四行      │
│ ＋段落 ⇧合 ✂拆│← 点卡片选中，右侧即编辑         │ · 操作按钮组    │

★ **左栏是「大纲」而不是「段落列表」**：段落可能几十上百个，大纲只显示
`ID + 句数 + 时长`，是**定位**用的；主区卡片流才是**编辑**用的。两个职责分开，
段落多了也不会挤。

★ **卡片流是刻意的选择**：分镜页已经用卡片流了，用户不需要学第二套
"多行文本 + 拖边界"的模型。（分镜页卡片流未虚拟化记在R-09，
但段落量级比分镜小得多，暂不处理。）

### 3.3 编辑器选型：不引入 AvalonEdit / Monaco / WebView2

工作台要的不是"一个完整 md 编辑器"，是"**能把稿子切成段落节点的编辑器**"：

- **存盘是 md**（`ContractJson.Utf8NoBom`，R-13 教训）→ 你在 Obsidian 里也能写
- **编辑是卡片流**（与分镜页一致）→ 零新依赖
- 段落内文本用 WPF 原生 `TextBox` 即可

### 3.4 ★★ 已实现：回车分段（用户习惯 = 数据模型）

> **用户习惯（2026-10-02确认）**：写稿时**回车分段**。
> 所以**一个回车就是一个段落节点**，不做任何"聪明的"自动切分。

**为什么只认回车，不按句号猜**

中文的语义边界不在句号上：`他说：'你去。'` 的句号在引号里，标点层分不出来；
`一是定义。二是分类。` 一句里两个逻辑步。而回车是**人已经替我们判好的边界**——
他觉得"这段说完了"才按的回车。想拆就多按一次回车，仅此而已。

**★ 已实现的两套切法（不许合并）**

| 函数 | 用在哪 | 规则 | 为什么 |
|---|---|---|---|
| `ScriptStore.Parse(text)` | 打字区文本 | **一个回车 = 一段** | 用户习惯的直译 |
| `ScriptStore.ParseMarkdown(md)` | 读 `script.md` | **按空行分段** | markdown 惯例（段间空一行） |

★ **踩过的坑**：存盘用 `\n\n`，读盘若按回车切，那行空行会变成一个空段落
→「写 3 段存进去，读出来6 段」，每开关一次多一倍。无头往返断言当场抓出来，已修。

另外：三种换行（`\r\n` / `\r` / `\n`）统一算一次回车（从Obsidian 粘进来的稿子
不该被切得七零八落）；末尾无回车也不丢段；空段落不静默丢弃（"这里要插一段"是有意义的信号）。

### 3.5 ★ 已定：局部重做的保证

改一段 → **只有那一段**标「待重录」，别的段录音照旧有效。
实现靠 `MarkTextChanged()` 逐段比对文本（打字区改动时，拿旧文本逐段对比，
只对真的变了的那几段动手）。这是"改第 3 段不用重录全篇"的保证，
30 条断言里专门守着这一条。

### 3.6 ★ 录音功能：界面已做，按钮全灰（按你要求）

```
● 录音    ↻ 重录    ▶ 试听    ⌁ 句打点     ← 全部 IsEnabled="False"
```

- **摆出来而不藏起来**：空壳按钮点不动会让人以为坏了；摆出来 + 灰掉 +
  一行"期二开发"，才是"这功能在排队"的诚实表达。
- 导出转写稿 / 应用到下游同样灰掉（跟录音是一批东西：没有实测时长就导不准）。

### 3.7 ★★ 待你想清楚：回车分段怎么往下游应用（本期只做了第一层）

**已落地的**：回车 → 段落节点（`ScriptBlock`，带永久 ID）。
**还没定的**：这个段落节点，怎么变成下游①粗剪 / ③分镜 认识的句子和镜头？

现在的状况是**中间少一层**：

```
回车分段  ✅ 已做      →  ScriptBlock[]     （段落节点，有 ID、无时间）
     ↓
句级切分     ❓ 待定     →  TranscriptSegment[]（有 start/end 的句子）
     ↓
镜头         已有       →  ShotRow[]
```

★ 三个具体问题等你拍板：

1. **一段 = 一句，还是一段要再切成多句？**
   回车分的段落未必是口播的"停顿单元"。比如一段里有三个 `。`，
   那导出时是 1 句（整段当成一句）还是 3 句（按标点再切）？

2. **没录音时，时间戳从哪来？**
   段落有字数、**没有实测时长**（期二才有）。三条路：
   ① 按字数占比摊到总时长（准到±几秒，但总时长得先知道）
   ② 先只出文字、时间戳留空（下游可能不接受，得看粗剪怎么读）
   ③ 不导出，等录完再导（最稳，但写作台就不能单独用了）

3. **粒度可能不匹配**：现在是"一段"，但下游要的是"一句"或"一镜"。
   如果一段 ≠ 一镜，中间这层要不要**可见**、能不能手动调？
   （比如粗剪页直接让你在段落上画分句点。）

★ 我的倾向（仅供你判断，不当结论）：**让回车分段等于"镜头级"单位**——
即一段 = 一镜。理由：④渲染与 ③分镜本来就以镜为单位，改一句不用重渲一镜是
这套流水线的核心价值；而且这样最省事——不需要额外的切句界面。
代价是：一句之内要有多个逻辑步时，一镜要装下它（渲染提示词里已经要求
"长句要让动效复杂些"，能兜住）。

### 3.8 与 Obsidian 的关系：单向、显式

| 时机 | 动作 |
|---|---|
| 打开写作台 | 读一次 `script.md` → 解析成段落节点 |
| 保存 | 由段落节点**整份重写** `script.md`（原子写、无 BOM） |
| 工作台开着时你在 Obsidian 改了 | **不管** —— 下次打开才读 |

★ 不做后台双向同步。理由：双向同步是分布式一致性问题，
《阅读管理页规划》已经为它写了 70% 篇幅，同一份稿子不值得再付一次。

## 4. 数据落点与模型

### 4.1 目录（`ProjectRef` 加两个属性，约 20 行）

```
项目\<项目名>\
  script.md                          ← 稿源（纯 md，可在 Obsidian 写）
  stages\00-script\
    script.json                      ← 段落节点（永久 ID / 顺序 / 文本 / 音频引用）
    audio\seg_s01.wav                ← 逐片录音（期二）
    takes\seg_s01-take2.wav          ← 重录留底（期二，默认只留最后一次）
```

★ 编号 `00` = ① 之前，**现有 01/03/04/05 一个都不用动**。

### 4.2 模型（沿用规划稿，命名已避开坑 2）

```csharp
public class ScriptDoc {
    public string SourceMdPath { get; set; } = "";
    public List<ScriptBlock> Blocks { get; set; } = new();
}

public class ScriptBlock {
    public string Id { get; set; } = "";      // ★ 永久 ID（s01…），复用 ShotRow 那套
    public int Index { get; set; }            // 顺序（会重排，不进文件名）
    public string Text { get; set; } = "";    // 稿子原文
    public string? AudioFile { get; set; }    // 录了才有
    public double? DurSec { get; set; }
    public int TakeCount { get; set; }
    public bool NeedsRerecord { get; set; }   // 改稿后自动标
    public List<double> SentenceMarks { get; set; } = new();  // ★ 片内句边界
}
```

★ `Id` 复用 V1.1.0 已落地的永久 ID 机制（`s01…`、与位置无关、永不复用、不进文件名）。
`EnsureShotIds` 的"只给空的补"策略照抄——**老项目打开时不该重排已有 ID**。

### 4.3 ★★ 唯一的技术接入点：产物就是一份 `transcript.json`

已核对 `Transcript.cs` 契约：`SchemaVersion` / `Language` / `Engine` / `Model` /
`AudioPath` / `AudioDurationSec` / `FullText` / `Segments[]`，
每段 `Index` / `StartSec` / `EndSec` / `Text` / `Words[]`。

```
老路：整段录音 ──▶ 外包 ASR ──▶ transcript.json
新路：稿子 + 分段录音 ──▶ 本地直接生成 ──▶ 【同一份 transcript.json】
```

→ **②③④⑤ 一行都不用改。** 这是整个方案最值钱的判断。

| | 老路 | 新路 |
|---|---|---|
| `StartSec/EndSec` 来源 | ASR 猜的 → **会漂**（实测差 56 秒） | 片段边界累加 → **零误差** |
| 稿子忠实度 | ASR 转写，可能改写 | **原文，零损耗** |

期一就要落地的「导出为转写稿」：没录音时 `StartSec/EndSec` 用**字数占比预估**
（`FinalScriptBuilder` 已有降级估算逻辑可复用），并把 `Engine` 标成 `script`、
把估算值在页面上显式标灰"时长为预估值"——**不许让预估值伪装成实测值**。
