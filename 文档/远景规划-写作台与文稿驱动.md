## 0. 一句话结论

你提的三件事（md 写作 / 分段录音 / 数据看板）**不是三个功能，是一条主线上的三段**——
合起来会把工作台从「处理已录好的音频」变成「从一张空白稿子长出成片」。

**其中有一个关键判断，全文最重要**：

> ★ **分段录音的价值不在「省事」，而在把「转写」这一环整个删掉。**
> 现在台词要走过「人说一遍 → 机器听一遍 → 文字」这条最脆弱的路
> （那条「要原始 ASR、不要整理成稿」的血泪规矩，实测差 **56 秒**）。
> 稿子一旦直接进工作台，台词就是原文，**零损耗、零对齐误差、不用外包**。

**以及一条最重要的建议**：

> ★★ **动手前先花半天验「听感」**（§2 期零）。
> 分段录音唯一可能致命的代价是「一段段录 → 听上去像朗诵不像说话」，
> 而读书博主的观众买的恰恰是娓娓道来的语感。这**只能实测，不能凭猜**。

## 2. ★ 核心设计：三段是同一份数据的三种视图

### 2.1 别做成两个独立功能

如果做成「工作台里塞个 md 编辑器」+「再加个录音按钮」两个独立模块，
必然掉进经典同步地狱：**稿子改了、录音对不上、镜头跟着错位**。

正确做法：它们是**同一份数据的三种视图**，共用一套段落节点。

```
写的一「段」        录的一「片」         出的一个「镜」
┌──────────┐      ┌──────────┐       ┌──────────┐
│ 第 3 段   │ ───▶ │ seg_03   │ ───▶  │ shot_03  │
│ 2 句 18秒 │      │ wav 18秒 │       │ mp4 18秒 │
└──────────┘      └──────────┘       └──────────┘
      ▲                                     │
      └───── 改稿 → 只重录这一片 → 只重渲这一镜 ─┘
```

★ **这条链最大的好处是「局部重做」**：
改第 3 段的稿子 → 只重录 `seg_03` → 只重渲 `shot_03`，**其余 50 镜一个字节都不动**。
而现在改一句台词，得重走「转写 → 粗剪 → 精剪 → 分镜 → 渲染」整整一圈。

### 2.2 ★★ 最优雅的接入点：产物就是一份 `transcript.json`

这是整个方案最关键的技术判断——**下游 ②③④⑤ 可以一行代码都不改**。

```
老路：整段录音 ──▶ 外包 ASR 转写 ──▶ stages\01-transcript\transcript.json
新路：稿子 + 分段录音 ──▶ 本地直接生成 ──▶ 同一份 transcript.json（格式完全一致）
```

`transcript.json` 的接口契约不变（每句带 `start` / `end` / `text`），
只是**来源从「机器听写」换成「稿子原文 + 片段实测时长」**。

- 老路的 `start/end` 是 ASR 猜的 → **会漂**（差 56 秒那个坑）
- 新路的 `start/end` 是片段边界累加出来的 → **零误差**

★ 所以这不是「给流水线加两个前置环节」，而是**换掉一个数据源，其余全不动**。

### 2.3 数据落点

```
项目\<项目名>\
  script.md                      ← ★ 稿子原文（纯 md，可在 Obsidian 里写）
  stages\00-script\
    script.json                  ← 段落节点（永久 ID / 顺序 / 文本 / 对应片段）
    audio\seg_<id>.wav           ← 逐片录音
    takes\seg_<id>-take<N>.wav   ← 重录留底（可选，默认只保留最后一次）
```

**为什么编号 `00`**：稿子是**① 转写之前**的环节，而现有编号 `01/03/04/05` 一个都不用动。
（现有 `02` 空缺——精剪的阶段目录，与本文无关。）

### 2.4 数据模型（拟）

```csharp
public class ScriptDoc {
    public string SourceMdPath { get; set; } = "";   // script.md
    public List<ScriptBlock> Blocks { get; set; } = new();
}

public class ScriptBlock {
    public string Id { get; set; } = "";      // ★ 永久 ID（s01/s02…），复用现有血统机制
    public int Index { get; set; }            // 顺序（会重排，不进文件名）
    public string Text { get; set; } = "";    // 稿子原文（来自 md）
    public string? AudioFile { get; set; }    // seg_<id>.wav，录了才有
    public double? DurSec { get; set; }       // 录了才知道
    public int TakeCount { get; set; }        // 录了几遍
    public bool NeedsRerecord { get; set; }   // 改稿后自动标
    public List<double> SentenceMarks { get; set; } = new();  // ★ 片内句边界打点
}
```

★ **`Id` 完全复用 V1.1.0 已落地的永久 ID 机制**（`ShotRow.Id` 那套：`s01…`、与位置无关、
永不复用、不进文件名）。这是本工程已经交过学费的东西，不该再交一次。

### 2.5 ★ 与 Obsidian 的关系（要定死，否则是坑）

你本来就用 Obsidian（`D:\Benny`）。所以 `script.md` 用**纯 md 存盘**，你可以在 Obsidian 里写。

但**同步策略必须是单向、显式**的，不做后台双向同步：

| 时机 | 动作 |
|---|---|
| 工作台打开写作台时 | 读一次 `script.md` → 解析成段落节点 |
| 工作台保存时 | 由段落节点**整份重写** `script.md` |
| 工作台开着时你在 Obsidian 改了 | **不管**——下次打开才读（避免双向冲突） |

★ 理由：双向后台同步是分布式一致性问题，本工程在「阅读管理页」那个规划里已经为它
写了 70% 的篇幅。**同一份稿子不值得再付一次这个代价**，「打开读一次 / 保存写一次」够用了。

## 3. ★★ 期零：先花半天验听感（不写代码）

**这是整份规划里最该先做的一步。不做它，后面几千行代码可能白写。**

一段一段录，段与段之间的「气口」是断的——听上去容易变成**朗诵**，而不是**说话**。
这是本方案**唯一可能致命**的代价，且**只能实测，不能凭猜**。

**怎么验**（用手机或现有麦克风就够，半小时出结果）：

1. 从《思辨与立场》稿子里挑 **10 段**（连续的一小段）
2. 一段一段录，录不好就重来
3. 原样拼起来，**不做任何后期**
4. 戴上耳机，从头听一遍

**判定与处置**：

| 结果 | 处置 |
|---|---|
| ✅ 听不出接缝 | 方案成立，按 §5 路线图开工 |
| ⚠️ 明显「一顿一顿」 | 先试三个补救再判：① 段尾留 200ms 气口 ② 段首 1 秒预备音 ③ 接缝加 **crossfade** |
| ❌ 补救完还是别扭 | 改做「**连录模式**」（见下），不做「一句一片」 |

★ **crossfade 在这里派上用场**：`工作台-待办清单.md` 的 **T-03** 还开着（一直等你一句话）。
分段录音正好给了它一个明确的用途——段间加 2~5ms 淡入淡出消掉接缝。
（注意：这会破掉「音频全程零处理」那条铁律，需单独立项验收。）

★ **兜底方案「连录模式」**（如果听感实在补不回来）：
一口气录 3~5 段再停，**只在段间打标记**（录的时候敲一下键记一个时间点），不真停。
→ **听感 = 老路，精度 = 新路**。这个兜底很重要，因为它意味着
**即使最坏情况发生，§2.2 那个「删掉转写环」的收益仍然拿得到**。

## 4. ★ 粒度是这个设计的开关

「一段话一录音」里的**「一段话」到底多大**，决定这套东西是神器还是刑具。
**这个数字必须在动手前定死。**

| 粒度 | 10 分钟稿 | 录起来 | 重录代价 | 听感 | |
|---|---|---|---|---|---|
| 一句一片 | ~90 片 | ❌ 极累 | ✅ 最小 | ❌ 最差 | |
| **句群一片 ★** | **~30 片** | ✅ 可接受 | 中 | ✅ 较好 | **推荐默认** |
| 自然段一片 | ~12 片 | ✅ 轻松 | ❌ 错一字整段重来 | ✅ 最好 | |

**建议**：默认 **2~4 句 / 15~25 秒一片**，录音台里给一个滑块现场调，
允许同一篇稿子**不同段落用不同粒度**（难念的段拆细，顺的段录长）。

| 交付 | 说明 |

## 6. 关于甘特图与 OKR：冷水，和更好的替代

**甘特图**解决「谁在什么时候做什么、会不会撞车」，**OKR** 解决「团队目标对齐」——
**两者都以「有多个人」为前提**。你是一个人：不存在撞车，也不需要对齐仪式。
而且要维护的数据量很大（每条任务填开始/结束/依赖/进度），最后会变成新的负担。

**但「看板」这个直觉是对的**，只是该看的板**不是抄来的框架，而是从你自己的数据里长出来的**：

| 指标 | 为什么别人算不出来 |
|---|---|
| **每支片的总耗时**（立项→出片，拆到每一环） | 只有工作台握着**全链路**时间戳 |
| ★ **哪一环返工最多**（重渲/拆合/重录次数） | ★ **这是独一份的**：市面上没有任何工具知道你「这一镜渲了三遍」——而这正是最该被看见的浪费 |
| **单镜渲染成本**（耗时 + 失败率） | 渲染留痕本来就落在 `stages\04-render\`，只是从没被汇总过 |
| **项目水位**（卡在第几步、卡了几天） | `project.json` 里就有，缺的只是一个视图 |

★ **OKR 如果真想要**，做成「年度目标的轻量追踪」就够：
`今年出 50 支片 → 现在 18 支 ▓▓▓░░ 36%`，一条进度条拉到底。**不要做成任务依赖图**。
